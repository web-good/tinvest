максимум, что могут дать 2 валидных голоса, это 2/4, а нужно минимум 3.

## Step 3 — сверка с ожиданием (§5.2, §6.3 спеки)

Опорный in-sample замер (§6.3, из брифа/`_comment`): `VolMult` 3.0 × `VolBaseDays` 20 → 2.297/43
(хвост 6 — 6 сделок без убытков), 4.0 × 20 → 2.171/31; `vol_window` in-sample 1.37–1.56.
Walk-forward подтверждает, что объём при строгом множителе даёт положительный pooled OOS (обе темы
выше 1), но **не подтверждает устойчивость узла** — калибровка каждого train-окна выбирала свой
множитель (1.5–2.5 в теме `volume`, 1–3 в теме `vol_window`), а не фиксированные 3.0–4.0 из
in-sample замера; узкая выборка OOS (2 валидных фолда) не позволяет отличить устойчивый рычаг от
шума.

Правило приёмки (Step 3 брифа): поле `UseVolume` входит в точку, только если тема объёма
(`volume` или `vol_window`, по правилу лучшей из двух — §5.2) большинством 3/4 держит одно значение
`VolMult` **и** её pooled OOS выше pooled OOS `screen` на узле 1×0 (дефолты).

- **Условие большинства**: не выполнено ни у `volume` (2.5/1.5, 2 валидных голоса), ни у
  `vol_window` (1/2, 2 валидных голоса) — в обеих темах максимум 2 валидных фолда из 4, три голоса
  математически недостижимы.
- **Условие pooled OOS против дефолтов `screen`** (сверено, хотя уже избыточно из-за провала
  первого условия): по постановлению контроллера компаратор — переснятый в Task 1 pooled OOS
  дефолтов на узле 1×0, **1.659/52** (`docs/superpowers/plans/task-1-report-mdmg.md:162`, замер
  2026-09-26, на день раньше сегодняшних прогонов). `volume` 2.152/21 выше, `vol_window` 1.842/24
  выше. Отдельно отмечаю: это сравнение проводится на данных **разных дней** (компаратор снят
  2026-09-26, темы — 2026-09-27), тогда как Task 11/13 сравнивают кандидатов на одном дне (Review
  Focus п.1 global-constraints); мой вердикт здесь **предварительный** именно по этой причине.
- Дополнительно (контекст из брифа): тема `screen` (Task 3) проголосовала за `UseVolume` 0 с
  результатом 0, 0, 1, 1 — это ничья 2/2, а не большинство 3/4, поэтому она **не закрывает** объём
  сама по себе (§5.2, «ничья 2/2 большинством не считается»). Здесь это не имеет значения для
  вердикта — обе темы объёма и так не проходят своё собственное условие большинства.

**Число сделок train у выбранных узлов.** Артефакт `RenderWalkForwardMarkdown`
(`internal/service/backtest/walkforward.go:286-330`) печатает по фолду только `InSamplePF`
(In-sample PF) — счётчик train-сделок нигде не сохраняется и не выводится (структура
`WalkForwardFold` не хранит число train-сделок победителя, только `OOSTrades`). **Фактическое число
train-сделок выбранных узлов не публикуется артефактом и здесь не оценивается**, чтобы не подгонять
число под ожидание брифа (около 20–25 на узлах 3.0+ при 12-месячном train, по §6.3).

- **Предварительный вердикт Step 3**: `UseVolume` **не входит** в собранную точку из этих тем —
