## Step 3 — сверка с опорными замерами

### `RSIUpper` (двугорбая ось, in-sample §6.6 — из `_comment` `cal_exit.json`)

Опорные точки: 55 → 1.130/136 (максимум, горб), 60 → 1.106, 70 (дефолт) → 0.951. **Ожидание брифа
не подтвердилось буквально.** Бриф предсказывал горб 55–60 как область консенсуса; фактическое
голосование разбежалось по всей оси — **60, 65, 90, 55** — все четыре значения разные, ни одного
повтора. Один голос (55, фолд 4) действительно лежит в горбе, второй (60, фолд 1) рядом с ним, но
третий (65, фолд 2) уже за горбом, а четвёртый (90, фолд 3) — на противоположном крае оси, в
плоском хвосте 0.90–0.97, никак не связанном с горбом 55–60. Разброс шире, чем у RTKM (где голоса
хотя бы поделились строго 2/2 между двумя значениями) — здесь совпадений нет вовсе, большинства нет
и подавно. `RSIUpper` остаётся на дефолте ядра **70**.

Условие брифа «связка `RSIUpper` 55 + стоп 0.8 оставляет 2024 год в минусе (−5 225 ₽) — записать,
если тема проголосует за 55» — **не сработало**: 55 получил только 1 голос из 4, большинства нет,
условие брифа не выполнено буквально. Записываю это явно, как того требует общее правило пакета
(«когда ожидание брифа не подтверждается, сказать прямо»).

### Трейл при `UseRSIExit=1` / `UseRSIExit=0` (in-sample §6.6 — из `_comment` `cal_trail.json`)

Опорный замер: при `UseRSIExit=1` трейл вреден — PF 0.89–0.95 (не выше дефолта 0.951/130); при
`UseRSIExit=0` лучший узел `TrailDailyATR` 0.5 даёт 1.046/126 при просадке 23 351 ₽ — заметно выше
дефолтной (14 848.91 ₽).

Фактическое голосование **согласуется по направлению для UseRSIExit=1**: единственный фолд с этим
значением (фолд 1) даёт in-sample PF 1.058 — не сильно выше дефолта, трейл действительно почти не
помогает при включённом RSI-выходе, как и предсказывал опорный замер. Но **три из четырёх фолдов
(2, 3, 4) перешли на `UseRSIExit=0`** — не единичный контрольный случай, а устойчивое большинство —
и внутри этого режима выбрали `TrailDailyATR=0.5`, тот самый узел, который опорный in-sample замер
называет лучшим при выключенном RSI-выходе (1.046/126). Направление согласуется, но **интенсивность
консенсуса (3/4, а не единичный случай) — новая ситуация для каталога** (см. Step 2).

### Гейт A (потолок стопа, урок AFKS)

Правило брифа: «если тема голосует за `UseTrail` 1, гейт A применяется к `min(StopDailyATR,
TrailDailyATR)`». Тема `trail` **не голосует** за `UseTrail=1` в смысле §5.2 — единственное
протестированное значение, без сравнения с альтернативой 0 (см. Step 2, тот же вывод, что и у
RTKM и у большинства тикеров каталога). **Гейт A по теме `trail` не задействуется: замены не
происходит, цена решения в PF равна нулю** — `StopDailyATR` в сборку из темы `trail` не входит
вовсе (это поле темы `risk`, Task 8), а `TrailDailyATR` не участвует в гейте, поскольку `UseTrail`
остаётся на дефолте ядра 0.

## Открытый вопрос для Task 11 (записан, не решается этой задачей)

**`UseRSIExit=0` получил настоящее большинство ≥3/4 (§5.2) — впервые для этого поля во всём
каталоге rsi_pullback** — но это большинство добыто **только в комбинации с принудительным
`UseTrail=1`**, зафиксированным структурой сетки `cal_trail.json`. Поле `UseTrail`, в свою очередь,
не набирает настоящего голоса (единственное протестированное значение) и по правилу §5.2 остаётся
на **дефолте ядра 0**.

Комбинация «`UseTrail=0` + `UseRSIExit=0`» **не измерена ни одной темой каталога**: `cal_trail.json`
тестировал `UseRSIExit∈{0,1}` только при `UseTrail=1`; `cal_exit.json` тестирует только `RSIUpper`,
фиксируя `UseRSIExit=1`. Ни одна сетка не пробовала `UseRSIExit=0` при выключенном трейле. Перенос
голоса `UseRSIExit=0` в собранную точку (где `UseTrail=0` по структурной причине) означал бы принять
значение поля из контекста, в котором оно не тестировалось, — прямая аналогия с предупреждением
§5.2 про арбитров `entry_stop`/`day_stop» («При конфликте — pooled OOS арбитра ниже, чем у любой из
двух тем по отдельности — в точку идёт один рычаг»), только для этой пары `trail`-полей арбитра
(`cal2_trail_stop` или аналог) в плане SVCB не предусмотрено. Записываю вопрос явно для Task 11,
не принимая решения: либо принять `UseRSIExit=0` как поле, измеряемое темой `trail` независимо от
статуса `UseTrail` (буквальное чтение §5.2 — «поле берётся из темы, которая его меряет»), либо
считать голос недействительным вне контекста, в котором он получен (по аналогии с логикой арбитров),
и оставить `UseRSIExit` на дефолте ядра **1**.

## Что это значит для дальнейшего плана

1. **Тема `exit` не даёт точке поля `RSIUpper`.** Ось, вопреки опорному in-sample горбу 55–60,
   голосует вразнобой (60, 65, 90, 55 — все разные), большинства нет вовсе. `RSIUpper` остаётся на
   **70**. Условие брифа про связку 55+стоп 0.8 не сработало буквально.
2. **Тема `trail` даёт настоящее большинство по двум осям (`TrailDailyATR=0.5`, `UseRSIExit=0`), но
   не по `UseTrail`** (структурно приколочен, не голос). Это первый случай в каталоге, когда
   `UseRSIExit` реально набрал большинство за значение, отличное от дефолта ядра — открытый вопрос
   сборки записан для Task 11, не решён здесь.
3. **Гейт A не понадобился ни разу** — ни в `exit`, ни в `trail`: `UseTrail` не набрал настоящего
   голоса, гейт применять не к чему.
4. В отличие от RTKM (обе темы `exit`/`trail` не дали точке ни одного поля), у SVCB тема `trail`
   потенциально даёт два поля — при условии, что Task 11 разрешит открытый вопрос о переносе
   `UseRSIExit=0` в контекст с выключенным трейлом в его пользу.
