# Дублирование ERROR-логов в тему Telegram «General»

Дата: 2026-08-11

## Задача

Все ошибочные логи приложения должны приходить в тему «General» Telegram-группы,
не переставая при этом писаться в stdout (логи контейнера) как сейчас.

## Область

Дублируются записи уровня `slog.LevelError` — то есть всё, что идёт через
`logger.ErrorContext`. `Warn` и `Info` остаются только в stdout.

Дублирование работает в основном приложении (`cmd/main.go` → `internal/app`).
CLI-утилиты (`cmd/backtest`, `cmd/pullscreen`, `cmd/divscreen`, `cmd/pullparity`)
вызывают тот же `logger.Init()`, но Telegram-копию не получают и ведут себя
в точности как раньше.

## Архитектура

Три части:

### 1. `pkg/logger` — tee-хендлер

`Init()` сейчас создаёт `slog.NewTextHandler(os.Stdout, …)`. Он оборачивается в
`teeHandler`, который:

- делегирует **каждую** запись в `TextHandler` — stdout-поток не меняется ни по
  объёму, ни по формату, дедуп и лимиты на него не распространяются;
- дополнительно отдаёт записи уровня `>= slog.LevelError` в sink, если тот
  установлен.

Sink хранится в `atomic.Pointer` и устанавливается отдельным вызовом:

```go
type ErrorEvent struct {
    Time    time.Time
    Message string
    Attrs   []slog.Attr
}

type ErrorSink interface {
    Publish(ErrorEvent) // обязан не блокировать
}

func SetErrorSink(s ErrorSink)
```

Отдельный сеттер нужен потому, что `logger.Init()` в `internal/app/app.go`
выполняется раньше инициализации Telegram-бота. Если sink не установлен,
`teeHandler` работает как обычный `TextHandler`.

Интерфейс намеренно узкий: `pkg/logger` не знает про Telegram и не зависит от
`internal`, зависимость направлена внутрь — `internal` реализует
`logger.ErrorSink`.

### 2. `internal/service/notification/errorlog` — sink

Живёт рядом с существующим `internal/service/notification/purchase_shares`.
Зависимости: `telegram.Client` (уже привязанный к чату и теме через
`telegram.NewTopicSender(bot, GroupChatID, 0)`), источник времени (интерфейс,
чтобы тесты были детерминированными).

Владеет буферизованным каналом и одной горутиной-воркером.

### 3. Точка сборки

Новый шаг `initErrorLogSink` в списке инициализации `internal/app/app.go`,
**после** `initTelegramBotClient`. Шаг создаёт sink, запускает воркер с ctx
приложения, регистрирует остановку в `pkg/closer` и вызывает
`logger.SetErrorSink`.

Если токен бота или `GroupChatID` пусты, sink не создаётся: приложение
стартует как раньше, без Telegram-копии.

## Поток данных

```
logger.ErrorContext(ctx, "не удалось выставить ордер", "ticker", "UGLD", "err", err)
        │
        ├──► TextHandler → stdout            (всегда, без изменений, полный поток)
        │
        └──► sink.Publish(ErrorEvent)        (неблокирующий)
                 │
                 ▼
          chan ErrorEvent (буфер 256)  ── полон? ──► dropped++ и мгновенный возврат
                 │
                 ▼  горутина-воркер
          1. дедуп: ключ = Message (без атрибутов), окно 5 мин
          2. общий лимит: не более 10 отправок за минутное окно
          3. прошло → отправка одним сообщением
             не прошло → suppressed[ключ]++
                 │
                 ▼  тикер раз в минуту
          сводка «⚠️ подавлено N ошибок: <топ-3 ключа × счётчик>» (если было что подавлять)
```

### Параметры и обоснования

| Параметр | Значение | Почему |
|---|---|---|
| Буфер канала | 256 событий | Переживает всплеск ретраев, не занимая заметной памяти |
| Окно дедупа | 5 минут | Ретрай-циклы gRPC укладываются в минуты |
| Общий лимит | 10 отправок за фиксированное минутное окно | Telegram режет группу на ~20/мин, а туда же пишут стратегии, новости и отчёты портфеля — половина лимита остаётся им. Фиксированное окно, а не token bucket: однозначно проверяется тестом «11-е сообщение в том же окне подавлено» и совпадает с периодом сводки |
| Период сводки | 1 минута | Быстрая видимость того, что подавлено |
| Потолок сообщения | 3800 символов | Лимит Telegram 4096, запас на служебные строки |

**Ключ дедупа — только `Message`, без атрибутов.** В ретрай-цикле атрибуты
меняются (тикер, id заявки, текст gRPC-ошибки с таймстампом), поэтому ключ с
ними не поймал бы дубли вообще. Сообщение стабильно и представляет класс ошибки.
Цена решения: одна и та же ошибка по пяти тикерам придёт в чат один раз, а
остальные четыре попадут в счётчик сводки; в stdout при этом видны все пять.

**`Publish` не блокирует никогда.** Логирование не имеет права ждать сеть. При
переполнении буфера событие теряется для Telegram (в stdout оно уже есть), а
счётчик `dropped` попадает в ближайшую сводку — молчаливых потерь нет.

**Всё подавленное и потерянное всплывает в сводке.** Тишина в чате означает
«ошибок не было», а не «мы их проглотили».

## Формат сообщений

Бот отправляет с `ParseMode: HTML`, поэтому весь динамический текст проходит
через `html.EscapeString` (как в `internal/service/news/format.go`). Без этого
сообщение вида `rpc error: … <nil>` уронит отправку в 400.

Одиночная ошибка:

```
🔴 <b>ERROR</b> · prod · 14:23:05
не удалось выставить стоп-заявку
ticker=UGLD err=rpc error: code = Unavailable desc = ...
```

- Время — МСК, как в остальных уведомлениях.
- Метка окружения — из `APP_ENV`, чтобы dev-прогон не путали с боевым.
- Атрибуты — плоским списком `key=value`; вложенные группы разворачиваются
  через точку (`order.id=123`).

Сводка подавленного:

```
⚠️ <b>подавлено 47 ошибок за минуту</b>
23 × не удалось получить свечи
19 × ошибка отправки в Telegram
5 × не удалось выставить стоп-заявку
+ 12 событий не попали в очередь (переполнение буфера)
```

Классы ошибок сортируются по убыванию счётчика; показываются первые три,
остальные схлопываются в строку `+ ещё K классов`. Строка про переполнение
буфера выводится только при `dropped > 0`.

## Защита от рекурсии

Отправка в Telegram сама может упасть. Если этот провал залогировать через
`logger.ErrorContext`, получится бесконечный цикл «ошибка отправки → попытка
отправить ошибку отправки». Поэтому:

1. Воркер sink'а **никогда** не вызывает `pkg/logger`. Свои сбои он пишет
   напрямую в `os.Stderr` через `fmt.Fprintf` — в логах контейнера они видны,
   в Telegram не идут.
2. `Publish` не делает ничего, кроме неблокирующей записи в канал: он не
   ходит в сеть и не может породить ошибку.

Воркер один, отправка последовательная — порядок сообщений в теме
соответствует порядку возникновения ошибок.

## Конфигурация

Новых переменных окружения нет. Тема «General» в форуме Telegram — это
`message_thread_id = 0`, что уже поддерживается
`Bot.SendMessageToTopic(chatID, 0, msg)`. Используются существующие
`TELEGRAM` (токен) и `TELEGRAM_GROUP_CHAT_ID`.

## Тестирование

TDD, фейковые часы и фейковый `telegram.Client`.

| Проверка | Пакет |
|---|---|
| ERROR доходит до sink, INFO и WARN — нет | `pkg/logger` |
| stdout-вывод сохраняется при активном sink | `pkg/logger` |
| без `SetErrorSink` нет паники (путь CLI) | `pkg/logger` |
| повтор в окне 5 минут подавляется, после окна проходит | `errorlog` |
| 11-е сообщение в том же минутном окне подавляется, в следующем окне проходит | `errorlog` |
| сводка приходит с верными счётчиками, включая `dropped` | `errorlog` |
| `Publish` не блокирует при полном буфере | `errorlog` |
| ошибка отправки не порождает новых событий (нет рекурсии) | `errorlog` |
| `<` и `&` в тексте ошибки экранируются | `errorlog` |
| сообщение длиннее 3800 символов обрезается | `errorlog` |

Гейт приёмки — `./bin/mage ci` (lint + `go test -race ./...` + проверка дрейфа
моков).

## Вне области

- Уровни `Warn` и `Info` в Telegram не дублируются.
- Перехват паник воркеров не добавляется.
- Отдельная тема под ошибки (`TELEGRAM_TOPIC_ERRORS`) не заводится: цель —
  именно General.
