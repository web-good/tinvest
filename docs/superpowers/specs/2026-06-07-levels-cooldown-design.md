# Levels strategy: level-aware re-entry cooldown — design

## Контекст и проблема

Стратегия `levels/strategy/core` (long-only, отскоки/ретесты от volume-profile уровней)
прогнана на RUAL H1 за 2024-12-06 — 2026-06-06 (отчёт `reports/level/RUAL_levels_Hour1_20260606_235721.md`).

Итог: 42 сделки, win rate 42.86%, PF 1.344, чистый PnL +8.77%, max DD 10.0% (11 902) —
просадка больше всего чистого профита. Анализ помесячного PnL по журналу сделок показал,
что почти всю просадку сделал один режим — боковик/распил весны 2026 (фев–апр'26 = −9054,
из них март'26 = −6477). В этом режиме стратегия раз за разом покупала один и тот же
уровень и ловила стопы. Показательны переоткрытия по сути на том же месте сразу после SL:

| Пара | Стоп → переоткрытие | Интервал | Результат переоткрытия |
|---|---|---|---|
| 33→34 | 19.03 06:00 → 07:00 | 1 бар | −2510 (худшая сделка) |
| 37→38 | 09.04 18:00 → 23:00 | 5 баров | −603 |
| 40→41 | 15.04 10:00 → 14:00 | 4 бара | +830 (выигрыш, другой уровень) |

Цель: подавлять повторные входы по тому же уровню, который только что отрабатывался,
не убивая редкие выигрыши на других уровнях.

Exposure (8.23%) и низкий CAGR **не** считаем проблемой — сознательный выбор для одного
инструмента. Диверсификация вне области этой работы.

## Решение: level-aware cooldown по недавнему отскоку (чистый, без состояния)

Ключевое ограничение архитектуры: `strategy.Decide` обязана быть **pure** (см.
`scalping/strategy/strategy.go` — "Decide must be pure"). Стратегию гоняют и бэктест-движок
(`internal/domain/backtest/engine.go`, последовательный цикл), и живой раннер
(`scalping/trade.go`, одноразовый запуск по cron, **без памяти между запусками** и без
разметки причины выхода в истории брокера).

Поэтому cooldown реализуем как **чистую функцию от свечей окна**: перед входом стратегия
сама пересчитывает, не давал ли *тот же самый* уровень support сигнал на отскок в последние
N баров. Это не требует ни внешнего состояния, ни хранилища, ни новых полей в `MarketData`,
ни правок движка/раннера — и работает идентично в бэктесте и в живой торговле.

### Что меняется

Только два файла:

1. `internal/service/trading_strategy/levels/strategy/core/core.go`
2. `internal/service/trading_strategy/levels/strategy/rusal/rusal.go` (стартовое значение)

`MarketData`, `engine.go`, `trade.go`, `model.Signal` — **не трогаем**.

### Новый параметр

В `core.Params` добавляется одно поле:

```go
CooldownBars int // после отскока от уровня не входить по нему ещё N баров; 0 = выкл (аддитивно)
```

Допуск касания и бычий тест переиспользуют существующие `LevelTolATR` и `ConfirmCloseFrac` —
отдельных параметров не вводим (YAGNI).

### Логика

В `core.decide`, во flat-ветке входа, после резолва `support` и прохождения существующих
gate'ов (`touched && notExtended && bullish`), **перед** `entryQualifies` — добавляется
проверка cooldown.

Если `CooldownBars > 0` и среди последних N **завершённых** баров (исключая текущий
бар-кандидат) есть хотя бы один, который сам был отскоком от *этого же* support, вход
подавляется (возвращается пустой сигнал).

«Отскок от уровня на баре j» определяется так:
- касание: `low_j <= support + LevelTolATR*ATR`
- бычий close: `bullishClose(high_j, low_j, close_j, ConfirmCloseFrac)` И `close_j > support`

Новая чистая функция-помощник рядом с `recentlyBelowLevel`:

```go
// recentBounceOff reports whether any of the last `lookback` completed bars
// (excluding the current bar) was itself a bounce off `level`: its low touched the
// level within tol AND it closed bullishly back above the level. Used to cool down
// repeated entries on a level that just stopped the strategy out.
func recentBounceOff(highs, lows, closes []float64, level, tol, confirmFrac float64, lookback int) bool
```

Сигнатура и границы зеркалят `recentlyBelowLevel`: `end := n-1` (исключаем текущий бар),
`start := end - lookback`, clamp `start` к 0.

### Граничные случаи

- **Текущий бар всегда исключается** — он не должен блокировать сам себя (как в
  `recentlyBelowLevel`).
- `CooldownBars <= 0` → проверка не выполняется (поведение идентично текущему).
- Окно короче N — сканируем сколько есть (clamp `start` к 0).
- **Сознательное упрощение:** «отскоком» считается касание + бычий close у уровня, а **не**
  полный набор входных gate'ов (room / RR / extension). Это чуть агрессивнее (блокирует и
  near-miss'ы у того же уровня), что для де-кластеризации churn желательно. Преимущество —
  не нужно пересобирать volume profile per-bar; используем уже посчитанные `ATR` и `support`.
- Cooldown проверяется только когда стратегия flat. Управление открытой позицией (hard SL /
  chandelier trail) — отдельная ранняя ветка в `decide`, её не касаемся.
- Взаимодействие с RETEST/BOUNCE: cooldown срабатывает до присвоения `Reason`, одинаково для
  обоих типов входа.

### Стартовое значение для RUAL

В `rusal.DefaultParams()` добавляется `CooldownBars: 10` (в ряд с `BreakoutLookback: 10`),
помечено как стартовая точка под калибровку. Поскольку cooldown привязан к уровню, большое N
не вредит выигрышам на других уровнях (сделка 41 на другом уровне не блокируется).

## Тестирование (TDD, table-driven, рядом с `core_test.go`)

1. `CooldownBars=0` → поведение не меняется (регрессия на существующих кейсах входа).
2. Отскок от уровня X на баре n-1 → вход по X на баре n подавлен.
3. Отскок от X был > N баров назад → вход разрешён.
4. Недавний отскок от *другого* уровня (вне `LevelTolATR` от X) → вход по X разрешён.
5. Текущий бар-кандидат сам себя не блокирует (отскок только на текущем баре → вход разрешён).
6. Юнит-тест `recentBounceOff` на границах окна (короткое окно, lookback<=0, clamp).

## Область и follow-up

- В области: правка `core.go` + `rusal.go`, тесты, единичный re-run бэктеста для сверки
  эффекта на просадку весны 2026.
- Вне области: живое наполнение состояния (не нужно — решение чистое), диверсификация,
  антираспиловый ADX-фильтр (отдельная возможная итерация), полная калибровка `CooldownBars`.

## Критерий успеха

Кластер переоткрытий по одному уровню в марте 2026 (сделки вроде 33→34) подавляется;
выигрыши на других уровнях (сделка 41) сохраняются; существующие тесты `core` зелёные при
`CooldownBars=0`.
