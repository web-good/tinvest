# Scalping RSI+MACD — дизайн стратегии

Дата: 2026-07-22
Ветка: `feat/scalping-rsimacd` (от `main`)
Статус: спека утверждена, реализация не начата

## Идея

Внутридневной лонг-скальпинг на 5-минутках. Входим на развороте из
перепроданности: быстрый RSI выходит из критической зоны вверх, и вскоре после
этого MACD подтверждает разворот пересечением линий **ниже нуля** (то есть
разворот происходит ещё в зоне медвежьего импульса, а не после того, как
движение уже отработано). Стоп — под минимум свечи RSI-кросса, тейк — кратный
риску, плюс альтернативный выход по классическому стохастику при выходе из
зоны перекупленности.

Стратегия ticker-agnostic: параметры одинаковы для всех инструментов,
per-ticker пакетов нет (появятся, если калибровка покажет расхождение).

## Размещение

- Пакет: `internal/service/trading_strategy/scalping_rsimacd/strategy/core`
  (директории с подчёркиванием в репо уже приняты: `trading_strategy`,
  `service_provider`).
- Реестр бэктеста: `internal/service/backtest/scalping_rsimacd_registry.go`,
  функция `ScalpingRSIMACDLookupOrGeneric(ticker)`.
- Флаг CLI: `-strategy scalping_rsimacd -interval Minutes5`.
- Грид: `data/params/scalping_rsimacd/grid.json`.
- `daylow` не затрагивается: он живёт на своей ветке и в `main` отсутствует.

Стратегия реализует существующий интерфейс
`scalping/strategy.Strategy` (`Ticker() / Lookback() / Decide(MarketData)`)
и дополнительно `Explain(MarketData) string` для режима `-explain`.

### Ограничение чистоты

`Decide` обязана быть чистой и **не хранить состояние между барами** — движок
вызывает её независимо на каждом баре и в бэктесте, и в live. Поэтому «память»
о сработавшем RSI-триггере не хранится в полях структуры, а восстанавливается
из серий на каждом баре (см. правило входа 3). Это главное архитектурное
ограничение, под которое подогнаны формулировки правил.

## Индикаторы

Всё уже есть в `pkg/indicators`, новых индикаторов не пишем:

| Индикатор | Функция | Выравнивание |
|---|---|---|
| RSI | `RSISeries(closes, period)` | длина = len(closes), нули на прогреве |
| MACD | `MACD(closes, 3, 6, 9)` | длина = len(closes), нули на прогреве |
| Стохастик | `StochasticSeries(highs, lows, closes, 14, 3)` | правое выравнивание, `len(ks) = n-13`, `len(ds) = len(ks)-2` |
| ATR | `ATR(highs, lows, closes, period)` | скаляр |

Стохастик короче серии цен — при индексации обязателен пересчёт смещения
(`ks[len(ks)-1]` — текущий бар, `ks[len(ks)-2]` — предыдущий), а не прямое
обращение по индексу бара.

`Lookback()` = 120 баров: с запасом покрывает прогрев Wilder-RSI (период 3–5),
MACD(3,6,9), стохастика (14+3) и окно подтверждения.

## Параметры

```go
type Params struct {
    RSIPeriod       int     // 3..5, грид
    RSIOversold     float64 // 20/25/30, грид — нижняя критическая зона
    MACDFast        int     // 3, фикс
    MACDSlow        int     // 6, фикс
    MACDSignal      int     // 9, фикс
    MACDConfirmBars int     // окно подтверждения MACD после RSI-кросса, грид 2/3/4
    ATRPeriod       int     // 14, единица измерения санитарных порогов риска
    StopBufferATR   float64 // стоп = low(RSI-бара) - StopBufferATR*ATR; грид 0/0.1
    RR              float64 // тейк = entry + RR*(entry-stop); грид 2/2.5/3
    MinRiskATR      float64 // 0.1 — отсечь вырожденно узкий риск
    MaxRiskATR      float64 // 3.0 — отсечь аномально широкий стоп
    EnableStochExit int     // 1/0, грид — выход по стохастику
    StochK          int     // 14, фикс
    StochD          int     // 3, фикс
    StochOverbought float64 // 80, фикс
    // Сессия (минуты от полуночи MSK)
    SessionStartMin int // 480  = 08:00
    SessionEndMin   int // 1020 = 17:00 (Пн–Чт)
    FridayEndMin    int // 840  = 14:00 (Пт)
}
```

Все поля — `int` / `float64` (флаги как `int` 0/1), чтобы reflection-калибровка
могла их свипать.

## Правила входа (только лонг)

На текущем баре `n` (последний закрытый) открываем лонг, если выполнено **всё**:

1. **Сессия.** Время бара в MSK попадает в окно: Пн–Чт `[08:00, 17:00)`,
   Пт `[08:00, 14:00)`. Сб/Вс — входов нет. При отсутствии `md.Times` (live-путь
   без времён) гейт пропускается — никогда не блокируем на отсутствии данных.

2. **Подтверждение MACD на текущем баре.** `macd[n-1] <= signal[n-1]` и
   `macd[n] > signal[n]` (пересечение снизу вверх), **и обе линии ниже нуля**:
   `macd[n] < 0 && signal[n] < 0`.

3. **RSI-триггер в окне.** Существует бар `t`, `n - MACDConfirmBars <= t <= n`,
   на котором RSI пересёк критическую зону снизу вверх с фиксацией на закрытии:
   `rsi[t-1] < RSIOversold` и `rsi[t] > RSIOversold`. Берётся **самый свежий**
   такой `t`.

   Трактовка «в течение трёх баров»: пересечение MACD допускается на самом баре
   RSI-кросса либо на любом из следующих `MACDConfirmBars` баров (по умолчанию
   3, то есть окно `t..t+3`). Более строгая трактовка (только последующие три
   бара, исключая сам бар кросса) отбрасывалась бы как излишне редкая —
   предыдущая стратегия (daylow) провалилась именно из-за нулевого числа сделок.

4. **Триггер не аннулирован.** Ни на одном баре из `(t, n]` минимум не пробивал
   уровень стопа: `min(Lows[t+1..n]) > stopLevel`, где
   `stopLevel = Lows[t] - StopBufferATR*ATR`. Дополнительно `Closes[n] > stopLevel`.

5. **Санитарная проверка риска.** `risk = Closes[n] - stopLevel`; требуется
   `MinRiskATR*ATR <= risk <= MaxRiskATR*ATR`. Без этого RSI(3) на «плоской»
   свече даёт вырожденный риск в копейки, а тейк — абсурдно близкий уровень;
   верхняя граница отсекает вход после аномально широкой свечи.

Вход по цене закрытия бара `n`.

### Стоп и тейк

- **Стоп:** `Lows[t] - StopBufferATR*ATR` — минимум свечи RSI-кросса.
  `StopBufferATR` по умолчанию 0 (чистый low, как задумано); значение 0.1
  участвует в гриде на случай систематического выбивания шумом.
- **Тейк:** `entry + RR*(entry - stop)`, `RR` из грида `{2, 2.5, 3}`.

Оба уровня фиксируются на входе в `Position` (движок это уже поддерживает —
`Position.StopLoss` / `Position.TakeProfit`) и на последующих барах **не
пересчитываются**.

## Сопровождение позиции

Приоритет проверок на каждом баре:

1. **SL** — `low <= pos.StopLoss`. Заполнение по `min(StopLoss, open)`.
2. **TP** — `high >= pos.TakeProfit`. Заполнение по `max(TakeProfit, open)`.
3. **Стохастик** (когда `EnableStochExit == 1`) — выход по **закрытию** бара, на
   котором `%K` вышел из зоны перекупленности сверху вниз:
   `%K[n-1] >= StochOverbought && %K[n] < StochOverbought`.
4. **EOD** — принудительное закрытие по закрытию последнего бара сессии
   (Пн–Чт с 17:00, Пт с 14:00). Позиция никогда не переносится через ночь и
   через выходные.

При одновременном касании SL и TP на одном баре выигрывает **SL** —
консервативное допущение, принятое в остальных стратегиях репо.

## Калибровка

Файл `data/params/scalping_rsimacd/grid.json`, две фазы:

```json
{
  "phases": [
    {
      "name": "entry",
      "keepTop": 6,
      "grid": {
        "RSIPeriod": [3, 4, 5],
        "RSIOversold": [20, 25, 30],
        "MACDConfirmBars": [2, 3, 4]
      }
    },
    {
      "name": "risk",
      "grid": {
        "RR": [2.0, 2.5, 3.0],
        "StopBufferATR": [0, 0.1],
        "EnableStochExit": [0, 1]
      }
    }
  ]
}
```

27 + 12 комбинаций против 864 у daylow — умышленно узкий грид: MACD(3,6,9),
стохастик (14,3,3) и границы сессии заданы правилами стратегии и не свипуются,
что резко сокращает пространство подгонки.

Команда запуска:

```
go run ./cmd/backtest -ticker <TICKER> -strategy scalping_rsimacd -interval Minutes5 \
  -calibrate data/params/scalping_rsimacd/grid.json -out ./reports/<TICKER> \
  -months 6 -test-months 3 -min-trades 20 -metric profit_factor
```

## Критерий приёмки (валидация edge)

Решение о жизнеспособности принимается **только** по pooled out-of-sample
profit factor на walk-forward (`-months 6 -test-months 3`), а не по
in-sample-результату лучшей комбинации. Пороги:

- pooled OOS PF >= 1.5 и >= 30 OOS-сделок суммарно по корзине тикеров →
  кандидат на live;
- PF в диапазоне 1.0–1.5 → edge не подтверждён, в live не тащим;
- сходимость всех комбо к одному результату или < 10 сделок → сетап слишком
  редок, диагностируем через `-explain` прежде чем что-либо менять.

Уроки daylow и scalping-adaptive прямо применимы: in-sample-результат ничего не
доказывает, а редкость сетапа обнаруживается только по числу сделок.

## Тестирование

TDD, table-driven тесты в `core_test.go` по образцу `daylow/strategy/core`:

- RSI-кросс без MACD-подтверждения в окне → нет входа;
- MACD-кросс **выше** нуля → нет входа;
- MACD-кросс на границе окна (`t+MACDConfirmBars`) → вход; на баре `t+N+1` → нет;
- пробой уровня стопа между `t` и `n` → триггер аннулирован;
- вырожденный риск (< `MinRiskATR*ATR`) и слишком широкий (> `MaxRiskATR*ATR`) → нет входа;
- стоп равен `Lows[t]` при `StopBufferATR = 0`; тейк = `entry + RR*risk`;
- сессия: бар в 07:55 и в 17:05 (Пн–Чт), в 14:05 в пятницу, суббота → нет входа;
- выходы: SL, TP, приоритет SL при одновременном касании, стохастик-кросс вниз
  через 80, EOD в 17:00 и в 14:00 в пятницу;
- `EnableStochExit = 0` → стохастик не закрывает позицию;
- отсутствие `md.Times` → сессионный гейт и EOD деградируют в no-op, вход
  остаётся возможным.

Плюс тест реестра (`scalping_rsimacd_registry_test.go`): дефолтные параметры,
парсинг частичного JSON поверх дефолтов.

## Что осознанно не делаем

- Нет шортов — только лонг.
- Нет HTF-фильтра тренда и классификатора режима: daylow показал, что они не
  спасают отсутствующий edge, а пространство подгонки раздувают.
- Нет трейлинг-стопа: сначала измеряем базовую конструкцию.
- Нет per-ticker пакетов до результатов калибровки.
- Нет live-раннера: сначала валидация на бэктесте, решение о live — отдельно.
