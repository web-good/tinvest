# Levels: внутрибаровое исполнение стопов (intrabar stop execution)

- Дата: 2026-06-07
- Ветка: `feat/levels-volume-profile-strategy`
- Статус: согласовано, готово к написанию плана

## Проблема

Стратегия levels ставит жёсткий стоп на `поддержка − 1·ATR` и трейлинг-стоп
(chandelier) на `recentHigh − TrailMult·ATR`. Но в бэктесте оба стопа
проверяются по **цене закрытия** часовой свечи (`in.price` = последний `close`
в `core.go`), а исполнение происходит по `c.Close` (`engine.go`).

Следствие: стоп срабатывает только когда свеча уже **закрылась** ниже стопа, и
сделка закрывается по этому close, а не по уровню стопа. Если бар резко падает и
закрывается далеко под стопом, смоделированный убыток оказывается больше
ожидаемого. В отчёте `reports/level/RUAL_levels_Hour1_*` это видно как сделки
−1.3% / −2.2% при «стопе в 1 ATR».

Хотим: выходить в момент пересечения стопа внутри бара, не дожидаясь закрытия —
и для жёсткого стопа, и для трейлинга. Семантика должна быть одинаковой в
бэктесте и (в будущем) в реальной торговле.

## Решённые при брейншторминге вопросы

- **База стопа:** оставляем стоп под уровнем (`поддержка − 1·ATR`). НЕ
  привязываем к цене входа. Осознанно принимаем, что убыток от входа может быть
  до ~2 ATR (вход выше поддержки) — это вне рамок данной задачи.
- **Статус live:** боевого раннера для levels пока нет — стратегия только в
  бэктесте. Поэтому код пишем только для бэктеста; для live фиксируем контракт.
- **Подход:** A — триггер по `low` в стратегии + гэп-аккуратное исполнение в
  движке. Отклонены: B (полная модель отложенной заявки — точнее, но тяжёлый
  рефактор; разница на практике мала) и C (slippage к выходам по close — не
  решает задачу, всё ещё ждём закрытия).

## Дизайн

Стратегия остаётся чистой (pure): она решает, ВЫХОДИТЬ ли и на КАКОМ уровне
(уже кладёт уровень в `sig.StopLoss`). Движок владеет механикой исполнения
(цена fill с учётом гэпа). Это сохраняет существующее разделение
ответственности.

### 1. `internal/service/trading_strategy/levels/strategy/core/core.go` — `decide()`

Меняем триггеры стопов с цены закрытия на low бара:

```go
switch {
case in.barLow <= hardSL:                       // было: in.price <= hardSL
    sig.Kind, sig.Reason = model.SignalSell, "SL"
case armed && in.barLow <= chandelier:          // было: in.price <= chandelier
    sig.Kind, sig.Reason, sig.StopLoss = model.SignalSell, "TRAIL", chandelier
}
```

- `armed` (арминг трейла) оставляем по `in.price` (close) — это консервативно:
  трейл не активируется, пока бар не закрылся в нужном плюсе.
- Уровни `hardSL` и `chandelier` считаются как сейчас (та же формула, тот же
  ATR/recentHigh). `sig.StopLoss` уже несёт уровень для обоих случаев.

### 2. `internal/domain/backtest/engine.go` — `Run()`, ветка `SignalSell`

Исполняем стоповые выходы по уровню стопа с поправкой на гэп, а не по close:

```go
case model.SignalSell:
    if p.qty != 0 {
        exitPrice := c.Close
        if sig.Reason == "SL" || sig.Reason == "TRAIL" {
            exitPrice = min(sig.StopLoss, c.Open) // builtin min (Go 1.25)
        }
        res.Trades = append(res.Trades, p.close(exitPrice, c.Time, sig.Reason))
    }
```

Логика `min(уровень, open)`:
- Бар открылся выше стопа и пробил его внутри → fill ровно по стоп-уровню.
- Бар открылся гэпом ниже стопа (`open < уровень`) → стоп срабатывает на
  открытии → fill по `open` (хуже стопа). Это честный учёт гэп-риска.
- `min(уровень, open)` всегда ≥ `c.Low` (триггер означает `low ≤ уровень`, а
  `open ≥ low`), поэтому fill всегда внутри диапазона бара.

Выходы с другими причинами (сейчас таких нет) по-прежнему исполняются по
`c.Close`.

### 3. Тесты

- `core_test.go`: табличные кейсы — `low` пробивает `hardSL` при `close` выше
  стопа (раньше выхода не было, теперь "SL"); то же для трейла ("TRAIL");
  негативный кейс — `low` выше стопа, выхода нет.
- `engine_test.go`: обычный пробой (`open` выше уровня) → fill по уровню; гэп
  вниз (`open` ниже уровня) → fill по `open`; не-стоповый Sell → fill по close.

### 4. Live (контракт на будущее, код НЕ пишем сейчас)

Документируем семантику, чтобы будущий боевой раннер совпадал с бэктестом:
стратегия каждый бар отдаёт `sig.StopLoss` как уровень отложенной стоп-заявки;
live-раннер выставит стоп-маркет через Tinkoff `StopOrders` API и будет двигать
его вверх вслед за трейлом. Честная оговорка: в реале гэп/проскальзывание
означают, что «убыток ≤ 1 ATR» — это цель/норма, а не математическая гарантия
(в отличие от бэктеста без slippage).

## Ожидаемый эффект

- Большинство SL-выходов подтянутся к уровню стопа (`поддержка − 1·ATR`) вместо
  случайного close → хвосты −2.2% ужмутся примерно до −1.x%.
- На гэпах убыток всё ещё может превысить 1 ATR — это корректно (реальный гэп-
  риск, раньше прятавшийся за исполнением по close).
- Стопы будут срабатывать раньше (по low внутри бара), поэтому число сделок и
  win-rate в новом бэктесте изменятся — это более реалистичный результат, не
  регрессия. После реализации нужно перегнать RUAL-бэктест и сравнить отчёты.

## Вне рамок (YAGNI)

- Take-profit как выход (его сейчас нет).
- Отдельное моделирование slippage (отдельный параметр конфига на будущее).
- Сам live-раннер и интеграция со `StopOrders`.
- Перенос стопа на базу входа (`вход − 1·ATR`) — сознательно отклонено.
