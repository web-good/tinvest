# Levels: структурный (swing-low) жёсткий стоп

Дата: 2026-06-07
Ветка: `feat/levels-volume-profile-strategy`
Стратегия: `internal/service/trading_strategy/levels/strategy/core`

## Проблема

Калибровка RUAL (Hour1, 2024-05 — 2026-06, грид из 324 комбинаций) не дала ни одной
прибыльной комбинации: лучшая по `expectancy`/`net_pnl` даёт Net PnL −1246 (−1.25%),
Profit factor 0.934, 22 убытка из 35 сделок. В журнале сделок видно, что убыток
формируют многочисленные мелкие выбивания по жёсткому стопу `SL` на барах 1–5 после
входа (сделки 16, 18, 20, 26 — стоп за 1–3 бара). Несколько крупных трейловых побед не
перекрывают толпу шумовых стоп-аутов.

Корень: жёсткий стоп привязан к фиксированной дистанции в ATR от цены входа, а не к
структуре графика. При входе на отбое от поддержки стоп оказывается впритык и
выбивается рыночным шумом до того, как сетап успевает отработать.

Дополнительно обнаружен рассинхрон: проверка качества входа считает стоп от поддержки
(`support.Price − SLMult×ATR`, `core.go:196`), а живой стоп при управлении позицией — от
цены входа (`entry − SLMult×ATR`, `core.go:149`). RR оценивается по одному стопу, а риск
берётся по другому.

## Решение

Перенести якорь жёсткого стопа `SL` с «дистанции от входа» на **структурный минимум** —
наименьший `low` за окно `SwingLowWindow` баров. И для проверки входа, и для живого
стопа использовать один якорь:

```
stop = recentLow(SwingLowWindow) − SLMult×ATR
```

где `recentLow` — минимум `low` за окно (зеркало существующего `recentHigh`).

### Почему это работает и почему не нужен отдельный «пол»

Скользящий минимум всегда `≤` цены входа (минимум за окно не выше лоу текущего бара, а
лоу `≤` цены входа). Значит `recentLow − SLMult×ATR` гарантированно не ближе к входу, чем
`entry − SLMult×ATR`, то есть стоп **никогда не получается теснее текущего**. Структура
сама обеспечивает минимальную дистанцию — отдельный параметр `MinStopATR` был бы
избыточен (никогда не срабатывал бы). Эффект: стопы строго расширяются ровно на глубину
структурного минимума, что и есть рычаг против шумовых выбиваний. Настройка рычага —
окно `SwingLowWindow`.

Числовой пример (entry=100, ATR=1, SLMult=1.5):
- узкая консолидация, recentLow=99.5 → стоп 98.0 (дистанция 2.0) — шире текущего 98.5;
- широкое основание, recentLow=97 → стоп 95.5 (дистанция 4.5) — заметно шире.

## Объём изменений (всё в пакете `core`, без новых пакетов)

1. **Helper `recentLow(lows []float64, window int) float64`** — зеркало `recentHigh`
   (`core.go:262`): минимум `low` за последние `window` баров, все бары если их меньше,
   `window ≤ 0` клампится на последний бар.
2. **`decideInput`** — новое поле `recentLow float64`.
3. **`Build`** — заполняет `recentLow` из `md.Lows` по окну `SwingLowWindow`.
4. **`decide()`**:
   - ветка управления позицией (`core.go:147-162`): `hardSL = in.recentLow − SLMult×ATR`
     (вместо `entry − SLMult×ATR`);
   - ветка входа (`core.go:195-199`): `stop = in.recentLow − SLMult×ATR` (вместо
     `support.Price − SLMult×ATR`).
5. **`Lookback()`** (`core.go:55`) — включить `SwingLowWindow` в максимум окна, чтобы
   движок подал достаточно свечей.
6. **`core.Params`** (`core.go:19`) — новый параметр:
   `SwingLowWindow int // bars to scan for the structural low anchoring the hard stop`.
7. **`rusal.DefaultParams()`** (`rusal.go:13`) — дефолт `SwingLowWindow: 10`
   (на Hour1 ≈ полтора дня; короче `ChandelierWindow=20`, т.к. для входа берём свежее
   локальное дно). Стартовое значение под калибровку.

### Трейл-стоп не трогаем

Chandelier-трейл (`TRAIL`, `core.go:150,159`) остаётся динамическим механизмом фиксации
прибыли. Меняется только жёсткий `SL`.

### Сознательный компромисс: пересчёт каждый бар

Архитектура stateless — стоп нигде не хранится, `decide()` пересчитывает его каждый бар;
`Position` (`scalping/strategy/strategy.go:6`) шарится со скальпинг-стратегией, поле под
хранение якоря добавлять не будем (YAGNI). Следствие: окно скользит вместе со сделкой —
обычно `recentLow` растёт и стоп подтягивается вверх (плюс), но при новом лоу стоп может
ослабнуть. Это затрагивает только поздние бары; лечим же ранние выбивания (бары 1–5), где
окно ещё совпадает с входным. Если ослабление окажется вредным — отдельной итерацией
добавим хранение якоря на входе (поле в `Position`).

## Калибровка

- В `data/params/rusal/levels_grid.json` добавить ось `SwingLowWindow`, например
  `[5, 10, 15, 20]`.
- Чтобы не раздувать грид (324 × 4 = 1296), предварительно прогнать короткую проверку,
  какие существующие оси реально влияют на исход (в прошлых отчётах часть комбинаций
  давала идентичные строки-дубли → мёртвые оси), и оставить в гриде только влияющие оси
  плюс новую `SwingLowWindow`. Финальный размер грида согласовать в плане.
- `SLMult` сохраняется как буфер ниже структурного минимума.
  `TrailMult`/`ChandelierWindow`/`TrailArmATR` — без изменений.

## Тестирование (TDD)

Тесты в существующих `*_test.go` рядом с `core.go`:

1. **`recentLow` helper** — табличный тест (зеркало `recentHigh`): окно меньше/больше
   числа баров, окно `≤ 0`.
2. **Якорь живого стопа** — позиция открыта, `recentLow` ниже входа ⇒
   `hardSL == recentLow − SLMult×ATR`; причина `SL` при `barLow ≤ hardSL`.
3. **Согласованность вход↔управление** — на баре входа стоп из ветки входа и якорь
   живого стопа считаются от одного `recentLow` ⇒ совпадают (тест на чинимый рассинхрон).
4. **Инвариант «не теснее прежнего»** — `recentLow ≤ entry ⇒` стоп `≥ SLMult×ATR` ниже
   входа.
5. **`Lookback`** — при большом `SwingLowWindow` возвращает достаточный размер окна.

## Критерий успеха

Прогон бэктеста RUAL с новым дефолтом против baseline
(`reports/level_new/RUAL_levels_Hour1_20260607_224555_best.md`: PF 0.934, 22 SL-выбивания):
ожидаем снижение числа ранних `SL` и рост Profit factor. Если PF не вырастает — фиксируем
отрицательный результат и переходим к walk-forward (`-test-months`) и/или смене
инструмента/направления.

## Вне объёма (YAGNI)

- Хранение якоря стопа на входе (поле в `Position`) — только если пересчёт каждый бар
  навредит.
- Фрактальный свинг-лоу (pivot по N соседям) — усложнение, пробовать только если
  скользящий минимум не сработает.
- Отдельные параметры `StopBufferATR` / `MinStopATR` — избыточны (см. выше).
- Risk-based position sizing — движок сайзит по кэшу (`Fraction`), не по риску; вне темы.
