# Дизайн: фильтр старшего тренда (HTF) для стратегии RUSAL

Дата: 2026-06-05
Статус: утверждён к реализации

## Контекст и проблема

Бэктест стратегии `internal/service/trading_strategy/scalping/strategy/rusal` за период
2024-06 — 2026-06 (1H свечи) показал отрицательные метрики во всех профилях
(`trend/range/robust/scalp`): profit factor 0.60–0.79, чистый PnL от −3% до −35%.

Диагностика PnL по причине выхода выявила единственный источник убытка — корзину
стоп-лоссов:

| Профиль | TRAIL | TP | SL | Итог |
|---|---|---|---|---|
| trend | +7 833 | +10 524 | **−39 044** | −20 712 |
| range | +3 795 | +2 770 | **−9 790** | −3 231 |
| robust | −28 | −2 525 | **−13 937** | −16 502 |
| scalp | +35 769 | −1 916 | **−68 968** | −35 195 |

Выходы по тейку и трейлу в плюсе — логика входа что-то ловит. Весь минус — стопы.
Причина: акция за период упала на ~19% (42 → 34 ₽), а стратегия long-only входила
в лонги **против нисходящего старшего тренда** и добегала до стопа.

Параметрами это не лечится: grid-перебор 243 комбинаций упёрся в PF 1.11 на 43
сделках за 2 года (статистический шум). Нужно изменение логики — фильтр, запрещающий
лонги против старшего тренда.

## Решение

Добавить фильтр старшего тренда на основе **настоящих дневных данных**: лонг разрешён,
только если последняя закрытая дневная свеча выше дневной EMA(N).

### Принятые решения

- **Источник тренда:** настоящие дневные свечи (`enum.Day1`), не прокси на 1H.
- **Правило:** `lastDailyClose > EMA(DailyCloses, N)`. Сравниваем именно последний
  **закрытый** дневной close (стабилен внутри дня, не дёргается интрадей).
- **Период:** `N` калибруемый, по умолчанию **200** (≈10 мес на дневках).
- **Охват:** гейт на **обе** ветки входа (тренд и флэт). Жёстко, без отдельной ручки
  охвата — лишняя поверхность для переоптимизации. «Dip in uptrend» сохраняется,
  ловля падающего ножа убирается.
- **Выключатель:** `TrendFilterPeriod = 0` полностью отключает фильтр (чистый A/B).
- **Выходы не трогаем:** фильтр влияет только на входы (Buy), продавать не мешает.

## Архитектура и компоненты

### 1. Модель данных — `strategy.MarketData`

Файл `internal/service/trading_strategy/scalping/strategy/strategy.go`.

Добавить поле:

```go
// DailyCloses are oldest-first closes of COMPLETED daily candles, aligned so the
// last element is the most recent day closed at/before the current bar. Empty if
// no higher-timeframe data is supplied.
DailyCloses []float64
```

Только closes — правилу «цена > дневной EMA» больше ничего не нужно (дневные H/L/V не
добавляем по YAGNI; при будущей потребности в дневном ADX расширим тогда).

Интерфейс `Strategy` **не меняется**. Ответственность за «только закрытые дни» лежит
на поставщиках `MarketData` (бэктест-движок и боевой раннер).

### 2. Стратегия — `rusal.go`

- Новый параметр в `Params`:
  ```go
  TrendFilterPeriod int // daily EMA period for the higher-timeframe long filter; 0 disables
  ```
  В `DefaultParams()` — `TrendFilterPeriod: 200`.

- В `Decide`: вычислить `trendUp`:
  - если `TrendFilterPeriod <= 0` → фильтр выключен, `trendUp = true` (пропускаем всё);
  - иначе если `len(md.DailyCloses) >= TrendFilterPeriod` → посчитать дневную EMA через
    `ema.Compute(md.DailyCloses, TrendFilterPeriod)`, `trendUp = lastDailyClose > emaLast`;
  - иначе (фильтр включён, но дневных данных меньше периода — холодный старт) →
    `trendUp = false` (не торгуем вслепую).

- Прокинуть `trendUp bool` в `decideInput` и в чистое ядро `decide`.

- В `decide`, в **обеих** ветках входа (`regimeTrend` и `regimeRange`): добавить
  `trendUp` в условие выдачи `SignalBuy`. Управление открытой позицией (SL/TP/TRAIL)
  не меняется.

### 3. Бэктест-движок — `engine.go` (ядро корректности: без lookahead)

Сигнатура `Run` расширяется:

```go
func Run(s strategy.Strategy, candles []Candle, dailyCandles []Candle, cfg Config) Result
```

`dailyCandles` — oldest-first дневные свечи (уже только завершённые, см. п.4).

На каждом 1H-баре с временем `t = candles[i].Time` заполняем `md.DailyCloses`:
- дневная свеча видна, только если её календарный день **строго раньше** дня `t`
  в зоне `Europe/Moscow`. Это исключает подсматривание текущего незакрытого дня.
- реализуем указателем `dj`, продвигаемым по отсортированному `dailyCandles`, пока
  `dailyCandles[dj]` относится к дню < дня `t`. `DailyCloses` = closes[0..dj).
  Сложность O(n+m), без пересчётов на каждом баре.

Вспомогательная чистая функция (тестируемая отдельно), например:
`visibleDailyCloses(dailyCandles []Candle, t time.Time, loc *time.Location) []float64`
— или эквивалентная инкрементная логика с указателем.

### 4. Обвязка — `cmd/backtest/main.go` + `internal/service/backtest/candles.go`

- В `run()` после загрузки 1H свечей — второй вызов:
  ```go
  dailyFrom := from.AddDate(-1, 0, 0) // +~250 торговых дней на прогрев EMA200
  dailyCandles, err := provider.Load(ctx, ticker, share.ID, enum.Day1, dailyFrom, to, refresh)
  ```
  Кэш кладётся в отдельный файл `RUAL_Day1.json` (имя формируется из интервала —
  конфликта с `RUAL_Hour1.json` нет). `CandleProvider` уже параметризован по интервалу
  и через `convertCandles` отбрасывает незавершённую свечу — дополнительная фильтрация
  завершённости в обвязке не нужна.

- `dailyCandles` пробросить в `runSingle`/`runCalibration` → в `domain.Run(...)` и в
  `svc.RunGrid(...)`.

- `RunGrid` (`internal/service/backtest/calibrate.go`) получает параметр
  `dailyCandles []backtest.Candle` и передаёт его в каждый `backtest.Run(...)`.

### 5. Боевой раннер — `internal/service/trading_strategy/scalping/trade.go`

- После 1H `GetCandles` — второй `GetCandles` с интервалом `enum.Day1`:
  лимит ~250, `from = now − 250 дней`.
- `DailyCloses` строить **только из завершённых** дневных свечей (фильтр по
  `IsComplete`), отбрасывая текущий формирующийся день — то же правило «только
  закрытые дни», что и в бэктесте. Реализовать в `buildMarketData` (или рядом),
  принимая дневной ряд вторым аргументом.

## Поток данных

```
Backtest:  CandleProvider.Load(Hour1) ─┐
           CandleProvider.Load(Day1)  ─┴─> Run(s, h1, daily, cfg)
                                            └─ per bar: visibleDailyCloses(daily, t) ─> md.DailyCloses
                                                                                       └─ Decide ─> trendUp gate

Live:      GetCandles(Hour1) ─┐
           GetCandles(Day1)  ─┴─> buildMarketData(h1, completedDaily) ─> md.DailyCloses ─> Decide ─> trendUp gate
```

## Обработка ошибок и крайние случаи

- **Холодный старт** (дневных данных < периода): фильтр включён → входы запрещены.
  На практике не срабатывает из-за годового лид-ина в бэктесте; в live первые ~200
  торговых дней истории всегда доступны через API.
- **Фильтр выключен** (`TrendFilterPeriod=0`): `trendUp=true`, поведение бит-в-бит как
  до изменения. Это база для регрессионных тестов.
- **Нет дневного ряда вообще** (`DailyCloses` пуст) при включённом фильтре: трактуется
  как холодный старт → входов нет.
- **Часовые пояса:** сравнение дней ведём в `Europe/Moscow`, чтобы граница торгового
  дня MOEX совпадала с дневной свечой.

## Обратная совместимость

- `Run` и `RunGrid` меняют сигнатуру → обновить вызовы в `cmd/backtest/main.go`,
  `calibrate.go` и затронутые тесты.
- Старые JSON-профили (`data/params/rusal/*.json`) не содержат `TrendFilterPeriod`.
  `ParseParams` накатывает их поверх `DefaultParams`, поэтому при перепрогоне они
  **унаследуют фильтр 200**. Для воспроизведения прежнего поведения — явно указать
  `"TrendFilterPeriod": 0`.
- `ParamRows` (рефлексия) автоматически выведет новое поле в отчётах — отдельной
  правки рендера не требуется.

## Тестирование

- **Юнит выравнивания** (чистая функция): дневная свеча того же или будущего дня не
  попадает в `DailyCloses`; попадают только строго более ранние дни.
- **Стратегия:**
  - при включённом фильтре Buy подавляется, когда `lastDailyClose < EMA`, и проходит,
    когда выше — в обеих ветках (trend и range);
  - `TrendFilterPeriod=0` воспроизводит прежнее поведение;
  - холодный старт (данных меньше периода) → входов нет.
- **Движок:** сценарий с проигрышным лонгом в даунтренде → после фильтра сделки нет;
  существующие тесты движка обновлены под новую сигнатуру и проходят.
- **Раннер:** `buildMarketData` отбрасывает незавершённый дневной бар.

## Валидация результата (после реализации)

- Прогнать профили с фильтром (деф. 200) и без (`TrendFilterPeriod=0`) и сравнить
  метрики, особенно корзину SL и max drawdown.
- Проверить устойчивость на нескольких окнах (`-months 6/12/18/24`), не только на
  текущем даунтренде.
- Не доверять единичному всплеску PF на малой выборке — смотреть exposure и число
  сделок.

## Вне области (YAGNI)

- Дневные H/L/V и дневной ADX/Donchian.
- Slope/наклон EMA и комбинированные правила (можно добавить позже отдельным режимом,
  если уровневый гейт оставит остаточные против-трендовые убытки).
- Отдельная настраиваемая «ручка охвата» (off/trend/both).
