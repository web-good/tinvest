# Разбивка дохода в алерте доходности портфеля (YTD)

Дата: 2026-06-02
Статус: согласован

## Цель

Добавить в Telegram-алерт «Доходность портфеля (с начала года)» три
информационные строки, показывающие суммарно за период (1 января → сейчас),
по всем счетам:

- **Купоны (чистыми)** — полученные купоны за вычетом удержанного налога;
- **Дивиденды (чистыми)** — полученные дивиденды за вычетом удержанного налога;
- **Прибыль от продаж** — реализованная прибыль/убыток по проданным активам.

Эти величины **информационные**: они не меняют `PeriodReturn` и `XIRR`.
Купоны и дивиденды, пришедшие деньгами, уже учтены в текущей стоимости портфеля
(а значит и в обеих метриках доходности); строки лишь дают разбивку источников.

## Решения (из брейнсторма)

- «Доход от продажи активов» = **реализованная прибыль** (выручка − цена покупки),
  берётся из `OperationItem.Yield` — Тинькофф считает её сам, cost-basis вручную
  считать не нужно.
- Купоны/дивиденды показываем **чистыми** (за вычетом удержанных налогов).
- Формат: **три отдельные строки**.
- Архитектура забора данных: **Подход A** — один расширенный cursor-запрос.

## Источник данных

Тот же `GetOperationsByCursor` (state EXECUTED, период = начало года … сейчас).
Релевантные типы операций (`OperationType`):

| Категория | Типы |
|---|---|
| Купоны (брутто) | `COUPON` (23) |
| Налог на купоны | `BOND_TAX` (2), `BOND_TAX_PROGRESSIVE` (33) |
| Дивиденды (брутто) | `DIVIDEND` (21), `DIV_EXT` (43) |
| Налог на дивиденды | `DIVIDEND_TAX` (8), `DIVIDEND_TAX_PROGRESSIVE` (34) |
| Продажи (реализованная прибыль) | `SELL` (22), `SELL_CARD` (7), `SELL_MARGIN` (18) |

Плюс уже используемые типы пополнений/выводов (для XIRR) остаются.

Расчёт:
- `couponsNet = Σ Payment(COUPON) − Σ |Payment(BOND_TAX, BOND_TAX_PROGRESSIVE)|`
- `dividendsNet = Σ Payment(DIVIDEND, DIV_EXT) − Σ |Payment(DIVIDEND_TAX, DIVIDEND_TAX_PROGRESSIVE)|`
- `realizedSaleProfit = Σ Yield(SELL, SELL_CARD, SELL_MARGIN)` (может быть < 0)

Налоговые операции в API приходят с отрицательным `Payment`; берём по модулю,
чтобы расчёт не зависел от знака, который отдаёт API.

## Архитектура (Подход A)

Один расширенный запрос на счёт; классификация в сервисе из той же выдачи.

1. **`pkg/client/grpc/model/operation.go`** — в `CashOperation` добавить поле
   `Yield float64` (реализованная доходность операции; значима для сделок).

2. **`pkg/client/grpc/converter/operation.go`** — в
   `ConvertCursorItemsToCashOperations` заполнять `Yield` из `item.GetYield()`
   (units + nano/1e9, по аналогии с `Payment`).

3. **`pkg/client/grpc/operations_service_client.go`**:
   - расширить список типов (сейчас `depositWithdrawalTypes`) доходными/налоговыми/
     продажными типами выше; переименовать переменную в нечто нейтральное
     (напр. `relevantOperationTypes`);
   - переименовать метод `GetCashFlowOperations` → `GetCashOperations` (в интерфейсе
     и реализации), сигнатуру не менять;
   - обновить doc-комментарий: метод возвращает все релевантные для расчёта
     доходности операции (пополнения/выводы + купоны/дивиденды/налоги/продажи).

4. **`internal/service/portfolio/yield/operations.go`** — добавить
   `aggregateIncome(ops []model.CashOperation) (couponsNet, dividendsNet, realizedSaleProfit float64)`.
   `toCashFlows` **не трогаем**: она по-прежнему отбирает только типы пополнений/
   выводов, поэтому XIRR-ряд не меняется (купоны/дивиденды не должны входить в XIRR
   как внешние потоки — это внутренняя доходность портфеля).

5. **`internal/domain/portfolio_yield.go`** — добавить поля
   `CouponsNet`, `DividendsNet`, `RealizedSaleProfit float64`.

6. **`internal/service/portfolio/yield/yield.go`** — после получения операций
   вызвать `aggregateIncome` (по агрегированным операциям всех счетов) и заполнить
   новые поля домена.

7. **`internal/service/portfolio/yield/notification/telegram.go`** — отрисовать три
   строки после блока сумм. Показываются **всегда** (не зависят от `StartValue`).
   - Купоны/дивиденды — обычными деньгами (всегда ≥ 0): `formatMoney`.
   - Прибыль от продаж — со знаком (может быть < 0): `formatSignedMoney`.

Обновляемые потребители при переименовании метода: единственный вызов в
`yield.go:41` и фейк `fakeOperationsClient` в `yield_test.go`.

## Тестирование

- **Конвертер** (`converter/operation_test.go`): `Yield` корректно заполняется из
  `OperationItem.Yield`.
- **`aggregateIncome`** (новый unit-тест в пакете yield): микс операций
  (купоны + налог, дивиденды + налог, несколько SELL с положительным и отрицательным
  Yield, плюс посторонние типы) → верные нетто-суммы; знак налога не влияет.
- **Нотификация** (`notification/telegram_test.go`): три строки присутствуют,
  отрицательная прибыль продаж отображается со знаком `−`.
- **Сервис** (`yield_test.go`): фейк возвращает доходные операции → сообщение
  содержит строки разбивки.

## Верификация на реальных данных

Заложить шаг проверки: убедиться, что `OperationItem.Yield` по операциям SELL
действительно равен реализованной прибыли (сверить с приложением Тинькофф на
1–2 реальных сделках). Если поле окажется ненадёжным — fallback на ручной cost-basis
обсуждается отдельно (вне текущего объёма).

## Вне объёма

- Изменение формул `PeriodReturn`/`XIRR`.
- Ручной расчёт cost-basis (пока полагаемся на `Yield` от API).
- Налоговые/комиссионные строки помимо чистки купонов/дивидендов.
