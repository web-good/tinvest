# Scalping Sell-Watcher — Design

**Date:** 2026-06-03
**Status:** Approved (approach A)

## Problem

Сейчас скальпинг-стратегия (`internal/service/trading_strategy/scalping`) запускается одним
cron-job `"1 8-23 * * 1-5"` — раз в час по будням. Один вызов `service.Trade` проверяет и вход
(Buy), и выход (Sell). Стратегия не торгует, а только шлёт уведомление в Telegram; исполняет
пользователь вручную.

Следствие: сигнал на выход (TP/SL) по уже открытой позиции тоже вычисляется не чаще раза в час.
Между часовыми тиками уведомления о продаже не приходят, и пользователь может опоздать с выходом
до ~1 часа.

## Goal

Когда в портфеле есть позиция, слать уведомления о продаже чаще, чем основной (часовой)
шедулер — отдельным, более частым «сторожем выхода», не меняя логику входа.

## Decisions

- **Частота сторожа:** каждые 5 минут — cron `"*/5 8-23 * * 1-5"`.
- **Данные:** те же 1h-свечи, включая текущий (формирующийся) бар. `Decide` переиспользуется
  как есть; TP/SL (ATR, chandelier) пересчитываются по текущей цене. Важно: текущий `Trade`
  уже запрашивает свечи `to=now`, т.е. формирующийся бар включён — отдельной логики данных
  не нужно.
- **Анти-спам:** без состояния — слать на каждом тике, пока сигнал на продажу активен. (Сознательный
  выбор пользователя ради простоты.)
- **Охват:** только тикеры, под которые есть зарегистрированная стратегия (`Decide` с TP/SL) И
  которые сейчас удерживаются в портфеле. Для бумаги без стратегии сигнал выхода вычислить нечем.

## Approach A — флаг режима на существующем `Trade`

Переиспользуем весь конвейер `Trade`; разница лишь в фильтрации.

### Changes

1. **`scalping/dto/trade.go`** — добавить поле `SellOnly bool`. По умолчанию `false` →
   текущее поведение (вход + выход).

2. **`scalping/trade.go` (`service.Trade`)** — в цикле по стратегиям:
   - если `in.SellOnly` и по инструменту нет открытой позиции (`posByID[id]` отсутствует) →
     `continue` до запроса свечей (не тратим gRPC и не генерим Buy);
   - после `Decide`: если `in.SellOnly` и `sig.Kind != model.SignalSell` → `continue`.

   Остальной путь без изменений: свечи `to=now` (форм. бар), `Decide`, сбор сигналов, отправка
   в Telegram.

3. **`scalping/notification`** — в sell-режиме слать тем же `notification.Trade`, но с другим
   заголовком (напр. «⚠️ Мониторинг выхода»), чтобы отличать от часового прогона. Способ передачи
   режима в рендер — на усмотрение реализации (доп. аргумент/функция); минимальная правка.

4. **`internal/app/app.go`** — добавить второй worker (dev: горутина; prod: cron-job),
   вызывающий `scalpingscheduler.NewSchedulerService(...).Trade(ctx, scalpingdto.Trade{
   Scheduler: "*/5 8-23 * * 1-5", SellOnly: true})`. Существующий часовой job остаётся как есть.

### Data flow

```
cron "*/5 8-23 * * 1-5"
  -> service.Trade(SellOnly=true)
     -> GetPortfolio
     -> для каждой удерживаемой бумаги (есть стратегия + позиция):
          GetCandles 1h (to=now, форм. бар) -> Decide
          -> если SignalSell: добавить в signals
     -> если signals != empty: tgClient.SendMessage(notification.Trade(signals, sellOnly))
```

Без состояния; шлёт на каждом тике, пока сигнал активен.

### Concurrency

Часовой job (минута 1) и сторож (минуты 0,5,10,...) могут запускаться близко по времени.
`Trade` без состояния и только читает данные + шлёт TG, поэтому параллельные вызовы безопасны.

## Testing

Табличные тесты на `service.Trade` в sell-режиме (моки `instrumentsClient`, `marketDataClient`,
`operationsClient`, `tgClient`):

- (а) есть позиция и `Decide` даёт Sell → одно уведомление;
- (б) есть позиция, сигнала нет → молчит;
- (в) позиции нет → инструмент пропущен, свечи не запрашиваются (мок `GetCandles` не вызван);
- (г) Buy-сигнал в sell-режиме игнорируется (нет уведомления).

Регрессия: в режиме по умолчанию (`SellOnly=false`) поведение `Trade` не меняется.

## Out of scope / unchanged

- Логика `Decide` и расчёт TP/SL.
- Калибровка и бэктест (`cmd/backtest`, `internal/service/backtest`,
  `internal/domain/backtest`).
- Автоматическое выставление ордеров (стратегия остаётся сигнальной).

## Alternatives considered

- **B. Отдельный метод `WatchExits`** — чётче разделение, но дублирует каркас (свечи, цикл).
- **C. Отдельный пакет/сервис sell-watcher** — избыточно, дублирует DI-проводку.

Выбран A: минимум кода, идентичная логика выхода, текущий `Trade` уже даёт нужные данные.
