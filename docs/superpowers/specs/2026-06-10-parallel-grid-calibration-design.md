# Параллельный перебор грида калибровки

**Дата:** 2026-06-10
**Ветка:** feat/momentum-daily-trend-cooldown (или отдельная feat-ветка под реализацию)
**Статус:** дизайн утверждён, ждёт плана

## Проблема

Калибровка momentum-стратегии перебирает грид комбинаций параметров последовательно.
`runCombos` (`internal/service/backtest/calibrate.go:51`) — это обычный `for` по
комбинациям, каждая из которых запускает полный бэктест (`backtest.Run`) на ~13k
часовых свечей. Гриды разрослись (добавлены `CooldownBars`, `MACDSlow`, фазовый
формат), и перебор стал заметно медленным. Машина 16-ядерная, но используется одно ядро.

Параллелить хотим **только перебор грида (CPU)**. Загрузку свечей (fetch через gRPC
Тинькофф) НЕ трогаем — чтобы не упереться в rate-limit'ы API и не ловить throttling.

## Решение

Превратить последовательный цикл в `runCombos` в ограниченный worker-pool на горутинах.

### Область изменений

Ровно одна функция: `runCombos` в `internal/service/backtest/calibrate.go`.

- `RunGrid` и `RunPhases` вызывают `runCombos` и ускоряются прозрачно, без изменений
  их сигнатур и поведения.
- **Фазы остаются последовательными** by design: фаза k+1 сеется от топ-`KeepTop`
  выживших фазы k (`RunPhases`, calibrate.go:112-147) — это смысловая зависимость,
  параллелить нельзя.
- Корзинный цикл по тикерам (`runBasket`, `cmd/backtest/main.go:387`) и любой fetch
  свечей — **не трогаем** (rate-limit).

### Число воркеров

Именованная константа рядом с `defaultKeepTop` (calibrate.go:25):

```go
// calibWorkers bounds the goroutine pool that evaluates grid combinations.
// Kept conservative so a calibration run does not peg the whole machine.
const calibWorkers = 4
```

Без CLI-флага. Тюнится правкой одной строки. (Решение пользователя: фиксированное N,
консервативно, машину целиком не забивать.)

### Детерминизм (критичное требование)

Результаты пишутся в заранее выделенный слайс по индексу комбинации:

```go
results := make([]CalibResult, len(combos))
// каждый воркер: results[i] = CalibResult{Params: combos[i], Metrics: m}
```

Воркеры не делят на запись общие ячейки (каждый индекс пишется ровно одним воркером),
поэтому мьютекс на запись не нужен. Порядок результатов на выходе **бит-в-бит** совпадает
с последовательной версией → `rankResults` и все числа в отчётах не меняются.

### Механика

Классический bounded worker-pool:

- Канал индексов `jobs := make(chan int)`; продьюсер шлёт `0..len(combos)-1` и закрывает.
- `calibWorkers` воркеров читают индексы, для каждого: `backtest.Run(b.Build(combos[i]), …)`
  + `backtest.Compute(…)`, пишут `results[i]`.
- `sync.WaitGroup` ждёт завершения всех воркеров.
- Канал на запись результатов НЕ нужен — пишем напрямую по индексу.

Если комбинаций меньше `calibWorkers`, лишние воркеры просто сразу завершатся (канал
закрыт) — отдельной обработки не требуется.

### Безопасность гонок (проверено при проектировании)

Каждая комбинация полностью независима:

- `b.Build(params)` создаёт свежий инстанс стратегии. Для momentum это
  `&Strategy{… barsSinceExit: cooldownSaturate}` (core.go:76) — своё мутабельное
  состояние на инстанс, не шарится между горутинами.
- `backtest.Run` (engine.go:84) строит локальный `portfolio` (`newPortfolio(cfg)`),
  входные слайсы `candles`/`dailyCandles` только читает — не мутирует.
- `backtest.Compute` (metrics.go:8) чистая: `Result` → `Metrics`.
- Единственный пакетный var движка — `mskLoc` (engine.go:14), иммутабельный
  `*time.Location`, только чтение.

Общего мутабельного состояния между комбинациями нет.

## Тестирование

- **Регрессия:** существующий `internal/service/backtest/calibrate_test.go` остаётся
  зелёным — он и есть гарантия, что ранжированный результат не изменился.
- **Новый тест под детектором гонок:** на известном маленьком гриде прогнать
  `RunGrid`/`runCombos` и сверить, что выход (порядок + метрики) идентичен ожидаемому
  эталону. Запускать в составе `go test -race ./internal/service/backtest/...`.
- **Бенчмарк:** `BenchmarkRunCombos` (или `BenchmarkRunGrid`) на репрезентативном
  гриде — подтверждение выигрыша «до/после». Nice-to-have, не блокер.

## Риски и митигация

Корректность конкуренции — это защитная логика, на которой нельзя экономить
(см. установку «не откладывать риски корректности на защитной логике»). Закрываем:

1. Гарантия порядка записью по индексу (каждая ячейка — один писатель).
2. Тест под `-race`.
3. Проверка независимости комбинаций, выполненная при проектировании (см. выше).

## Вне области (YAGNI)

- CLI-флаг `-workers`, авто-`GOMAXPROCS` — отклонено пользователем в пользу
  фиксированной константы.
- Параллелизм fetch свечей — отклонено (rate-limit).
- Параллелизм фаз и тикеров корзины — невозможно/нежелательно (зависимости / rate-limit).
