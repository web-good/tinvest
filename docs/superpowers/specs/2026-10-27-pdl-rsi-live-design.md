# pdl_rsi live — гость раннера счёта rsi_pullback

Дата: 2026-10-27. Статус: дизайн.

## Зачем

Владелец хочет торговать pdl_rsi (Hour1, бэктест-стратегия, `docs/pdl_rsi/strategy.md`) так же,
как сейчас торгуют rsi_pullback, rsi_zone и gap_fade: на том же брокерском счёте, тем же токеном,
тем же живым раннером. Сейчас нужно только подготовить всё к бою. Ни один тикер не включается:
тикеры, деньги и бумага остаются решением владельца, он включит их сам через env.

## Цели

- Новый гость раннера счёта: пакет `internal/service/trading_strategy/pdl_rsi/live`, адаптер
  `adapter.Strategy` по образцу `rsi_zone/live` и `gap_fade/live`.
- Реестр live содержит **все** пакеты тикеров pdl_rsi, которые есть сейчас (gazp, lent, mdmg, nvtk,
  svcb, vtbr). Каких тикеров торговать, решает env `PDL_RSI_TICKERS`, а не код.
- Раннер учится работать с гостем, у которого часовой таймфрейм, хотя сам он остаётся 30m.
- Сверка live-сборки с бэктестом: `cmd/pullparity -strategy pdl_rsi`.
- Документация механики `docs/pdl_rsi/live.md`, строка в CLAUDE.md, ключи в `env/local.env.example`.

## Не цели

- Не включать торговлю и не наполнять вселенную по умолчанию.
- Не перекалибровывать литералы. Литерал SVCB устарел: до одновременного входа он был без TrendEMA,
  а по нынешним правилам ядра даёт PF 0.98 на 256 сделках. Это решение владельца при включении;
  в `docs/pdl_rsi/live.md` достаточно одной строки «перед включением тикера проверь, что литерал
  откалиброван на действующем ядре».
- Буст доли LAG_BOOST к pdl_rsi не применяется, как и к gap_fade.
- Отдельного счёта, токена и файла стейта нет: всё общее с раннером.

## Анти-цели (провал, даже если «работает»)

- Хоть один ордер при `PDL_RSI_TRADE_ENABLED` не задан или false.
- Live принимает решение не на том часовом баре, который видел бы бэктест. Например, решение по
  получасовому бару или повторный BUY на уже отработанном часе.
- Позиция pdl_rsi без биржевого стопа.
- Изменение поведения rsi_pullback, rsi_zone или gap_fade. Их тесты и pullparity должны давать те же
  результаты, что до изменения.

## Ограничения и решённое

### Конфиг (`internal/config/pdl_rsi.go`), по образцу `RSIZoneConfig`

- `PDL_RSI_TICKERS`: по умолчанию пусто, и тогда гость не подключается (`Enabled()` как у rsi_zone,
  пустые строки не считаются).
- `PDL_RSI_BUY_PCT`: по умолчанию 5.
- `PDL_RSI_TRADE_ENABLED`: по умолчанию false.
- `PDL_RSI_NOTIFY_ENABLED`.
- Тема Telegram `TELEGRAM_TOPIC_PDL_RSI`, sender `GetPDLRSISender` по образцу `GetRSIZoneSender`.
- Подключение в `internal/service_provider/service.go`: последним гостем после gap_fade. Отсюда
  приоритет входа: rsi_pullback → rsi_zone → gap_fade → pdl_rsi. Занятый тикер pdl_rsi не берёт: это
  общее правило раннера, менять его не надо.

### Адаптер (`pdl_rsi/live`)

- `Name()` = `"pdl_rsi"`, `Label()` = `"PDL RSI"`.
- `Decider(ticker)`: `core.NewWithParams(ticker, time.Hour, <литерал>)` из реестра.
- `DesiredStop`: стоп заморожен на входе и равен уровню, который ядро строит в `exitLevels`:
  `fill − stopDistance(fill, EntryATR)`, где `stopDistance` учитывает `StopATR` и `MaxStopPct`.
  Причина `"SL"`. Для этого из ядра экспортируется одна функция уровня стопа. Ядро и live должны
  считать уровень одной функцией, а не двумя копиями формулы. Трейла у pdl_rsi нет; лесенка RSI —
  это выход по закрытию, а не стоп.
- `Reconstruct`: как у rsi_zone — `rebuild.LastBuyTime` плюс `rebuild.WeekdayDailyATRBefore` с
  `DailyATRPeriod` литерала; при нулевом ATR — ошибка. Цена входа — средняя цена брокера, от неё
  считается и стоп после рестарта, как у rsi_zone. *(Решение Claude.)*
- `Notify`: своя тема, ошибка доставки логируется как ERROR, как у rsi_zone.
- Сторожевой тест реестра: у каждого зарегистрированного литерала `StopATR > 0`, иначе биржевого
  стопа нет. По образцу `TestDropBounceLiveTickersAreRegistered` второй тест проверяет: тикер из
  `PDL_RSI_TICKERS` в `env/*.env.example`, если он там задан, обязан быть в реестре.

### Часовой таймфрейм в 30m-раннере

Раннер сейчас зашит на 30m: `marketdata.Assemble` тянет `Minutes30`, `barSpan = 30m`,
`maxBarAge = 60m`. Решение такое: необязательный интерфейс в `livecore/adapter`, например
`BarInterval` с методом, который возвращает интервал свечей стратегии. Стратегия без него остаётся на
30m, поэтому остальные гости не меняются. Раннер берёт интервал гостя для трёх вещей:

1. сборка MarketData: свечи `Hour1` нужного окна `Lookback()` плюс те же дневки. Лимит API для часа —
   до 3 месяцев на запрос, поэтому размер чанка зависит от интервала;
2. `entryBarTime`: шаг назад на один бар интервала гостя;
3. свежесть входа: BUY по свободному тикеру принимается, только если последний завершённый часовой
   бар закрылся не раньше одного шага cron (30m) назад. Это пасс сразу после закрытия часа (cron
   `1,31 6-23 * * *`, то есть :01). На пассе :31 вход по тому же часу молча пропускается. Если пасс на
   закрытии часа пропущен, вход не догоняется: поздний вход не равен входу бэктеста.
4. решение по открытой позиции (SELL ядра) принимается один раз на каждый завершённый час. В запись
   стейта добавляется необязательное поле времени открытия последнего решённого бара (`omitempty`,
   старые записи и 30m-гости его не пишут и не читают). Если на пассе последний завершённый час новее
   записанного, ядро решает по нему, и это догоняет пропущенный пасс. Самый частый случай — час
   23:00–23:50: пасса в 00:01 нет, и этот час решается на 06:01, продажа уходит по рынку, когда торги
   откроются. Если пропущено несколько часов подряд, решается только последний; это расхождение с
   бэктестом описывается в `live.md`. *(Решение Claude: без догоняния выход по цели и по кресту RSI на
   последнем часе вечерней сессии терялся бы каждый день, а менять cron для всех гостей запрещают
   анти-цели.)*
5. страховочная работа сопровождения идёт на **каждом** пассе, как у всех гостей, и правило свежести
   её не касается: перестановка снятого или отсутствующего биржевого стопа, сверка размера заявки,
   закрытие записи ушедшей из портфеля позиции. Гейт стоит внутри `manage` перед вызовом ядра, а не
   в `assemble`. *(Решение Claude: следует из анти-цели «позиция без стопа».)*

Протухание (данных нет дольше интервала плюс шаг cron) даёт алерт тем же путём, что и сейчас.

`freshEntryGrace` остаётся общим (2 часа) и часовому гостю хватает.

### Вход: тот же день, что и сигнал

Бэктест покупает на открытии следующего часа только той же будничной даты. Live должен воспроизвести
это ровно: пасс, который покупает, идёт в дату сигнального часа, и в эту дату после сигнального есть
ещё часовой бар (сигнал на последнем часе сессии не покупает). Как ядро это решает сейчас
(`Decide` или движок бэктеста), проверяет исполнитель. Если правило живёт в движке, live повторяет
его через `adapter.EntryWindow` или проверку в адаптере. Подтверждение — pullparity.

### Выходы

Цель (TP по high ≥ цели), выход по кресту RSIExit вниз и лесенка ядро отдаёт как SELL на закрытии
часа, раннер продаёт рыночной заявкой, как и цель rsi_pullback. Стоп — биржевая заявка. Известное
расхождение с бэктестом: тот исполняет цель по её уровню, live — по рынку после закрытия часа. Его
надо описать в `live.md`, а не чинить.

### Сверка

`cmd/pullparity -strategy pdl_rsi`: та же сборка MarketData (Hour1), что у live, против движка
бэктеста на истории. Сигналы и выходы по барам должны совпасть.

## Оставлено исполнителю

- Имя и форма необязательного интерфейса интервала, где хранить шаг cron для правила свежести.
- Где в ядре pdl_rsi живёт правило «покупка в ту же дату» и как его повторить в live.
- Раскладка тестов. Нужны как минимум: адаптер (стоп, реконструкция, нет стопа без ATR), раннер
  (часовой гость решает только на пассе после закрытия часа и не решает на :30; 30m-гости не
  изменились), конфиг (по умолчанию выключен), e2e по образцу `gapfade_e2e_test.go`.
- Текст `docs/pdl_rsi/live.md` — только механика, по правилам документации для rsi_pullback.
