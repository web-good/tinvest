# Reversion: опциональная модель исполнения стопа (close / интрабар)

**Дата:** 2026-07-10
**Ветка:** `feat/reversion-stop-orders` (продолжение несмерженной функциональности биржевых стопов)
**Статус:** дизайн утверждён пользователем

## Задача

Сделать интрабарное исполнение защитного стопа в reversion-стратегии опциональным.
Выбор задаётся параметром на уровне тикера (`core.Params`): либо стоп проверяется по
итогу закрытия часовой свечи (close-модель), либо интрабарно (`low ≤ уровень`, в live —
реальная биржевая стоп-заявка). **Дефолт — close-модель** (решение пользователя).

Параметр влияет и на бэктест, и на live-раннер (решение пользователя): close-модель у
тикера означает, что live НЕ выставляет биржевой стоп и выходит только по сигналу ядра
на закрытии часа — полная согласованность бэктеста и live. Мотивация: июньские
калибровки делались под close-модель; интрабарный перепрогон (см.
`docs/reversion/intrabar-rerun-2026-07.md`) показал, что UGLD/EUTR заметно теряют под
интрабаром, а NVTK почти нет.

## 1. Параметр

Новое поле в `core.Params`:

```go
UseIntrabarStop int // 0 = стоп по close часовой свечи, выход по рынку на закрытии (дефолт); 1 = биржевой стоп: срабатывание интрабарно по low, в live — реальная стоп-заявка
```

- Zero-value (0) = close-модель → существующие пакеты тикеров без изменений получают
  дефолт.
- Тип int, как у остальных флагов — поле доступно reflection-калибровке grid-поиском.

## 2. Core (общая семантика бэктеста и live)

`DesiredStop` не меняется: обе модели считают один и тот же уровень (max из SL / ATRSL /
TRAIL). Меняется только STOP-ветка `manage()`:

| Аспект | `UseIntrabarStop=1` (текущее поведение ветки) | `UseIntrabarStop=0` (новый дефолт) |
|---|---|---|
| Триггер | `in.low > 0 && in.low ≤ уровень` | `in.price (close) ≤ уровень` |
| Источник maxFav для TRAIL | `Position.PrevMaxFavorablePrice` (заявка стояла с прошлого бара) | `Position.MaxFavorablePrice` (решение на close — весь бар известен) |
| `sig.StopLoss` | = уровень → движок филлит `min(уровень, open)` | НЕ ставится → движок филлит по close (fallback существует, покрыт тестом с d4894a8) |

Порядок приоритетов выходов един для обеих моделей:
STOP(SL|TRAIL|ATRSL) → OB → RSI50 → BE → RSIOS → EMAX.

### Сознательные отличия от июньской close-модели (бит-в-бит не воспроизводится)

1. **Приоритет.** В июне OB стоял выше SL/TRAIL, а ATRSL — ниже BE. Единый порядок
   (STOP первым) проще; коллизия «стоп и перекупленность в одном баре» практически
   невозможна, а при коллизии стопа с RSI50/BE филл одинаков (по close) — меняется только
   метка причины выхода.
2. **Филл SL/TRAIL.** В июне SL/TRAIL филлились в `min(уровень, open)` при триггере по
   close — оптимистичный fill-bias (отмечен в ревью Fable-5 2026-07-09). Честная
   close-модель филлит по close: в live продажа рыночным ордером идёт сразу после
   закрытия часа, то есть ≈ close.

## 3. Live

- **buyPass** (`placeInitialStop`): при `UseIntrabarStop=0` стоп-заявка после входа НЕ
  выставляется (ранний return до `stops.Place`).
- **managePass**: блок синхронизации стоп-заявки (repost при росте трейла,
  sizeMismatch-реконсиляция, снятие stray-заявки) выполняется только при
  `UseIntrabarStop=1`. Для close-тикера выход происходит штатным путём: ядро на
  закрытии часа видит `close ≤ уровень` и отдаёт SELL → существующий путь
  cancel-if-any + рыночная продажа.
- **Переходное состояние:** если у close-тикера в стейте висит `StopOrderID`
  (заявка осталась после переключения флага с интрабара), managePass снимает её,
  чистит `StopOrderID/StopPrice/StopReason` в стейте и шлёт уведомление. При ошибке
  снятия — alert, ретрай на следующем тике (двойной защиты не возникает: новая заявка
  для close-тикера не ставится).
- Детект «позиция исчезла → сработал наш стоп» не меняется: он завязан на непустой
  `StopOrderID` и для close-тикера (пустой ID) сводится к существующей чистке стейта.

## 4. Раскладка боевых тикеров (решение пользователя)

- **NVTK** → `UseIntrabarStop: 1` (интрабарный перепрогон: PF 5.762→4.842, защита
  биржевым стопом почти бесплатна). Обновить комментарий калибровки в `nvtk.go`.
- **UGLD, EUTR** и все остальные пакеты тикеров → дефолт 0 (close-модель) — возврат к
  семантике их июньской калибровки. EUTR остаётся кандидатом на перекалибровку под
  интрабар (вне скоупа).

## 5. Тесты

- `core_test`: close-режим — триггер по close; НЕТ срабатывания, когда low проколол
  уровень, а close вернулся выше; трейл от текущего MaxFav (а не PrevMaxFav);
  `sig.StopLoss == 0`. Интрабар-режим — существующие тесты без изменений.
- live-тесты (`service_test.go` и соседние): после покупки close-тикера стоп-заявка не
  ставится; у close-тикера с оставшимся `StopOrderID` заявка снимается и стейт чистится;
  интрабар-путь (NVTK-подобный) ведёт себя как раньше.
- Гейт: `./bin/mage ci` (lint + `go test -race ./...` + mock-drift).

## 6. Финальный отчёт по прогонам (требование пользователя)

После имплементации — перепрогон walk-forward трёх боевых тикеров в их ИТОГОВОЙ
конфигурации (UGLD/EUTR — close-модель, NVTK — интрабар), теми же параметрами окон и
fixed-грида, что в `docs/reversion/intrabar-rerun-2026-07.md`. Результат — сводный
документ `docs/reversion/stop-mode-final-2026-07.md`:

- таблица по каждому тикеру: июньский close-baseline vs интрабарный перепрогон
  2026-07-10 vs финальная конфигурация;
- ожидание для контроля корректности: UGLD/EUTR в финальной close-конфигурации должны
  вернуться ≈ к июньским цифрам (не бит-в-бит — окна сдвинуты, филл SL/TRAIL честный по
  close); NVTK — совпасть с интрабарным перепрогоном (его параметры не меняются);
- существенные расхождения с ожиданием — разобрать в отчёте, а не замалчивать.

Отчёты кладутся в `reports/<TICKER>/stopmode/`. Содержание сводного документа
обязательно презентуется пользователю в финальном ответе (не только путём к файлу).
