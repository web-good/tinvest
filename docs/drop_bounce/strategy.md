# drop_bounce — отскок после большой красной свечи в перепроданности

Бэктест-стратегия, только лонг, таймфреймы 5m, 15m, 30m и 1h (`-interval Minutes5|Minutes15|Minutes30|Hour1`; другие cmd/backtest отклоняет). Правила одинаковы на всех четырёх: таймфрейм задаёт только шаг свечи (`step`), через который определяются свеча исполнения и `FillBy`; пороги в процентах и периоды индикаторов в свечах не масштабируются (стоп и фильтр размаха меряются в дневных ATR и от таймфрейма не зависят) — на 5m и 1h те же 0.6% и RSI(6) означают другое событие, чем на 15m. Позиция может переноситься через ночь. Код: `internal/service/trading_strategy/drop_bounce/strategy/core`, привязка к бэктесту — `internal/service/backtest/drop_bounce_registry.go`. Спека: `docs/superpowers/specs/2026-10-09-drop-bounce-rework-design.md`.

## Вход

1. Свеча-сигнал красная и её тело не меньше `MinDropPct` процентов: `(open − close) / open · 100 ≥ MinDropPct`.
2. RSI(`RSIPeriod`) по Уайлдеру на close этой свечи ниже `RSIEntry`. Пока истории меньше `RSIPeriod + 1` свечей, сигнала нет.
3. Подтверждение зелёной свечой (`GreenWaitBars > 0`, по умолчанию 3): покупка не сразу после свечи-сигнала, а после первой зелёной свечи (close > open) за ней. Зелёная должна прийти не позже чем через `GreenWaitBars` свечей после сигнала, в ту же дату МСК; между ними только незелёные свечи (красные и доджи). Вторая и следующие зелёные вход не дают, ожидание через ночь не переносится. Если между сигналом и зелёной несколько свечей проходят условия 1–2, сигналом считается ближайшая к зелёной. Ниже «свеча-триггер» — зелёная свеча, а при `GreenWaitBars = 0` — сама свеча-сигнал (вход как раньше, сразу после неё).
4. Окно: свеча-сигнал — Пн–Пт МСК, начинается не раньше `StartHour:00`; свеча исполнения (через один шаг после свечи-триггера) лежит в ту же дату, что и триггер. Сигнал на последней свече дня на утро не переносится.
5. Дневной ATR: Уайлдер `DailyATRPeriod` по завершённым дневкам Пн–Пт (сессии выходного дня отброшены — они в разы уже и тоньше). Считается на свече-сигнале и уходит в сигнал (`Signal.ATR`); движок замораживает его на позицию (`Position.EntryATR`). Если стоп или фильтр размаха включены, а ATR посчитать нельзя (дневок меньше `DailyATRPeriod + 1`), сигнала нет. Сигнала нет и тогда, когда стоп, отложенный от close свечи-триггера, ушёл бы в ноль или ниже.
6. Фильтр размаха дня (опционально): при `MaxDayRangeATR > 0` размах дня `high − low` от начала даты МСК до свечи-триггера включительно (свечи ожидания зелёной входят) не больше `MaxDayRangeATR · ATR`. День, уже прошедший больше, пропускается. Нет данных о размахе дня — фильтр не блокирует. `MaxDayRangeATR = 0` выключает фильтр.
7. Объёмный фильтр (опционально): при `VolMult > 0` объём свечи-сигнала (не зелёной) не меньше `VolMult` средних объёмов `VolBars` свечей перед ней (сама свеча в среднее не входит, свечи с нулевым объёмом — тоже). Нет объёмов, истории меньше `VolBars` свечей или все объёмы нулевые — фильтр не блокирует. Среднее не учитывает время суток: утренние свечи тяжелее, и утренние падения проходят фильтр легче. `VolMult = 0` выключает фильтр.
8. Покупка по open свечи, следующей за свечой-триггером (`Config.EntryAtNextOpen`). Сигнал уровней не несёт: стоп и профит считаются от цены исполнения.
9. Исполнение только в ближайший слот: сигнал несёт `FillBy = время свечи-триггера + шаг`, и если этой свечи в данных нет (дыра в вечерней сессии, тонкий тикер), движок сигнал отбрасывает, а не покупает по open следующего утра.

Пока позиция открыта, новые сигналы игнорируются.

## Выход

Проверяется на каждой свече удержания, включая свечу входа, по порядку; срабатывает первое условие.

1. **SL** — low свечи ≤ `вход − StopDailyATR · ATR`, где ATR — замороженный на входе (у позиции без него — текущий дневной). Новые дневки за время сделки стоп не двигают. Движок исполняет по `min(стоп, open)`: ночной гэп ниже стопа продаётся по open.
2. **PROFIT** — только на свече входа: её close ≥ `вход · (1 + ProfitPct/100)`. Продажа по close. На следующих свечах правило не действует.
3. **RSI** — RSI(`RSIPeriod`) пересёк `RSIExit` снизу вверх: на прошлой свече ниже, на текущей не ниже. Продажа по close.
4. **STOCH** — сглаженный %K стохастика (`StochPeriod`, сглаживание SMA(`StochSmooth`), 1 — сырой %K) пересёк `StochExit` снизу вверх. Продажа по close.

**Выход только в плюс** (`ExitInProfit = 1`, по умолчанию): крест RSI или %K, закрывшийся на цене входа или ниже, выход не даёт, а взводит его — продажа по close первой следующей свечи, закрывшейся выше цены входа, с причиной того индикатора, чей крест был в сделке (нового креста ждать не нужно). Пока выход взведён, работает SL. Крест ищется на свечах сделки (со свечи входа) внутри окна `Lookback`; при включённом правиле окно не меньше 200 свечей. `ExitInProfit = 0` — продажа на кресте при любой цене.

Выхода по концу дня нет. Нулевой порог выключает свой выход (`StopDailyATR`, `ProfitPct`, `RSIExit`, `StochExit`). Неверный период стохастика выключает этот выход.

## Параметры (`core.Params`)

| Поле | По умолчанию | Смысл |
|---|---|---|
| `MinDropPct` | 0.6 | минимальное падение тела свечи-сигнала, % |
| `RSIPeriod` | 6 | длина RSI для входа и выхода |
| `RSIEntry` | 30 | вход, если RSI ниже |
| `RSIExit` | 70 | выход при пересечении снизу вверх (0 — выключен) |
| `ExitInProfit` | 1 | 1 — крест RSI или %K в минусе откладывает выход до первого close выше входа, 0 — выход на кресте |
| `StochPeriod`, `StochSmooth` | 14, 3 | период %K и его сглаживание |
| `StochExit` | 80 | выход при пересечении %K снизу вверх (0 — выключен) |
| `ProfitPct` | 1 | профит на close свечи входа, % (0 — выключен) |
| `StopDailyATR` | 0.5 | стоп ниже цены входа в дневных ATR (0 — выключен) |
| `DailyATRPeriod` | 14 | период дневного ATR по будним дневкам |
| `MaxDayRangeATR` | 0 | вход, только если размах дня до сигнала не больше этого числа дневных ATR (0 — фильтр выключен) |
| `VolMult` | 0 | вход, только если объём свечи-сигнала не меньше этого числа средних (0 — фильтр выключен) |
| `VolBars` | 20 | сколько свечей до сигнала входит в средний объём |
| `StartHour` | 8 | начало окна сигналов, час МСК |
| `GreenWaitBars` | 3 | ждать первую зелёную свечу не дальше этого числа свечей после сигнала и входить после неё (0 — вход сразу после сигнала) |

История (`Lookback`) — `max(64, 4·RSIPeriod+2+GreenWaitBars, StochPeriod+StochSmooth+2, VolBars+1+GreenWaitBars)` свечей, а при `ExitInProfit = 1` и включённом выходе RSI или STOCH — не меньше 200: она задаёт первую торгуемую свечу и то, насколько далеко назад достаёт поиск креста в сделке.

Литерал тикера — пакет `internal/service/trading_strategy/drop_bounce/strategy/<ticker>/` с четырьмя функциями, по одной на таймфрейм: `ParamsMinutes5()`, `ParamsMinutes15()`, `ParamsMinutes30()`, `ParamsHour1()`. Каждый новый тикер заводится сразу со всеми четырьмя (ненастроенный таймфрейм — явно выписанные дефолты ядра) и снимком всех четырёх в тесте пакета. Регистрация — строка в `dropBounceRegistry` (`ticker: {ParamsMinutes5, ParamsMinutes15, ParamsMinutes30, ParamsHour1}`); запись бесключевая, поэтому без любого из четырёх таймфреймов код не компилируется. Литерал принадлежит своему таймфрейму и на другие не переносится; тикер без пакета на всех таймфреймах берёт `core.DefaultParams`. JSON из `-params` / `-calibrate` частично переопределяет поля литерала запущенного таймфрейма. Стартовая сетка — `data/params/drop_bounce/grid_example.json`, сетки тикера — `data/params/drop_bounce/<ticker>/`.

## Запуск

```
go run ./cmd/backtest -ticker GAZP -strategy drop_bounce -interval Minutes5 -months 6
go run ./cmd/backtest -ticker GAZP -strategy drop_bounce -interval Minutes15 -months 12
go run ./cmd/backtest -ticker GAZP -strategy drop_bounce -interval Minutes30 -months 12
go run ./cmd/backtest -ticker GAZP -strategy drop_bounce -interval Hour1 -months 12
go run ./cmd/backtest -ticker GAZP -strategy drop_bounce -interval Minutes15 -months 24 -calibrate data/params/drop_bounce/grid_example.json
```
