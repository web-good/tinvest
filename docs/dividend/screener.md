# Дивидендный фундаментальный скринер

Отбирает и ранжирует ликвидные дивидендные акции RUB-вселенной по качеству
дивиденда (устойчивость выплаты, долговая безопасность, рост, качество бизнеса,
оценка, доходность) и служит **двум потребителям**:

1. **Бот-команда `/dividend_screener`** — по запросу присылает в Telegram топ-25
   ранжированных имён + статистику отсева (`service.Send`).
2. **Golden X** — фундаментальный бонус `+0..3` к buy-Score стратегии
   (`RankProvider.RankBonus`), чтобы при прочих равных подсвечивать сигналы на
   фундаментально крепких дивидендных именах.

> **Роль (уточнена 2026-07-21).** Это **сито ликвидности + фундаментальный
> ранжир на службе Golden X**, а не самостоятельный торговый сигнал. Он не
> предсказывает доходность — он гарантирует, что фунд-бонус получают только
> крупные платящие имена, и упорядочивает их по абсолютному качеству дивиденда.

Код: `internal/service/screener/dividend/` (сервис + рендер + бонус),
`internal/service/screener/dividend/rank/` — **чистое ядро** (gate + пилляры +
composite, без I/O).

## Источник данных

- `InstrumentsClient.Shares` → берутся только `DivYieldFlag == true` с непустым
  `AssetUID`. Несколько инструментов на один актив (напр. обычка+преф одного
  эмитента) группируются по `AssetUID`; бонус разливается на **все** ID актива.
- `InstrumentsClient.GetAssetFundamentals(uids)` → `model.Fundamentals` на актив.
- Результат кэшируется на `defaultTTL = 24h`; `RankBonus`/`Top` дёргают
  `ensureFresh` (ленивая переподгрузка по TTL).

**Единицы полей `GetAssetFundamentals` (подтверждены живой валидацией 2026-07-21):**
`yield` и `payout` — **проценты** (8.0 = 8 %, 88 = 88 %); `MarketCapitalization`
— **в рублях**. Пороги в `DefaultConfig()` — на этой шкале, деления на 100 нет.

**Важное свойство proto3.** Поля fundamentals — `float64` с `omitempty`:
«значения нет» и «ровно 0.0» неразличимы. Правило ядра: **`0` в fundamental-поле
трактуется как «нет данных», а не как реальный ноль.** Отсюда две защиты ниже —
нейтральный payout и нейтрализация вырожденного перцентильного пула.

## Ворота отсева (`gate`)

Компания отсеивается (`GateReason != ""`, `Composite == 0`), если срабатывает
одно из оснований. Порядок проверки:

| Причина (`GateReason`) | Условие | Смысл |
|---|---|---|
| `нет дивиденда` | `yield <= 0` | не платит — **единственное «жёсткое» основание по фунду** |
| `низкая ликвидность` | `MarketCapitalization < MinMarketCap` (₽50 млрд; в т.ч. 0 = нет данных) | отсекает micro-cap/невыгруженные |
| `тонкий free-float` | `FreeFloat < MinFreeFloat` (0.07; в т.ч. 0 = нет данных) | отсекает имена с околонулевым свободным обращением (неторгуемые) |
| `yield trap` | `yield >= 20 %` **и** (`payout > 100 %` **или** `NetDebt/EBITDA > 3` **или** `FCF < 0`) | подозрительно высокая доходность на слабом фунде |
| `долг > порога` | `NetDebt/EBITDA > MaxNetDebtToEbitda` (4.0) | чрезмерный рычаг |
| `payout > порога` | `payout > MaxPayoutPct` (140 %) | выплата не покрывается прибылью |

`yield` = `ForwardAnnualDividendYield`, а при его отсутствии (0) —
`DividendYieldDailyTtm` (`yieldOf`).

**Что НЕ отсеивает (по дизайну).** Отсутствие EBITDA или payout (0 из-за
proto3-omitempty) **больше не исключает компанию** — иначе банки (у которых
EBITDA неприменима) и любое имя с невыгруженным payout выпадали из ранжира
(до фикса 2026-07-21 gate `EbitdaTtm>0 && payout>0` резал ~80 % вселенной,
включая SBER/LKOH/SNGSP/MTSS/PHOR). Теперь такие поля учитываются **нейтрально**
в пиллярах (см. ниже).

## Пилляры и composite

Composite = `100 × Σ(weight × pillar)`, веса суммируются в 1.0:

| Пилляр | Вес | Как считается |
|---|---|---|
| **Sustainability** | 0.30 | `0.7 × payout-fit + 0.3 × (FCF > 0)` |
| **Safety** | 0.25 | `leverageScore(NetDebt/EBITDA)`: <0 → 1.0; ≤1 → 0.9; ≤2 → 0.7; ≤3 → 0.4; иначе 0.15 |
| **DivGrowth** | 0.15 | перцентиль `FiveYearAnnualDividendGrowthRate` среди выживших |
| **Quality** | 0.15 | перцентиль `ROIC` (фолбэк на `ROE`, если ROIC=0) |
| **Valuation** | 0.10 | `1 − перцентиль(EV/EBITDA)` — ниже мультипликатор лучше |
| **Yield** | 0.05 | `min(yield, 14 %) / 14 %` — доходность с потолком |

**payout-fit** (`payoutFit`): 1.0 в идеальной зоне `[30 %, 60 %]`, линейно к 0 к
краям (0 и `MaxPayoutPct`=140 %).

### Две нейтрализации «нет данных»

- **Нейтральный payout** (`sustainabilityPayout`): при `payout <= 0` возвращает
  0.5 вместо 0 → `Sustainability = 0.7×0.5 + 0.3×(FCF>0)`. «Неизвестно» не
  вознаграждает и не штрафует платящее имя.
- **Нейтральный вырожденный пул** (`percentileOrNeutral`/`hasSpread`): если у
  всех выживших метрика одинакова (напр. `FiveYearAnnualDividendGrowthRate`
  приходит нулём по всей вселенной), перцентиль = 0.5 для всех, а не 0. Без
  этого 15 % веса composite превращались в мёртвую константу 0 и занижали все
  оценки. Применяется к DivGrowth, Quality, Valuation.

Перцентили считаются пулом **только по выжившим** (не по всей вселенной) через
`indicators.PercentileRank` (R-7-совместимый ранг, строгое `<`).

## Фундаментальный бонус для Golden X

Composite (0..100) отображается в бонус **абсолютными полосами**
(`bonusFromScore`), чтобы величина бонуса **не зависела от состава вселенной**:

| Composite | Бонус |
|---|---|
| ≥ `BonusScoreT3` (73) | +3 |
| ≥ `BonusScoreT2` (67) | +2 |
| ≥ `BonusScoreT1` (56) | +1 |
| иначе | 0 |

Пороги откалиброваны 2026-07-21 по перцентилям композита **ликвидной** вселенной
(n≈41): p25≈56, p50≈67, p75≈73. Отсеянные воротами имена бонуса не получают (0).

Бонус входит в buy-Score Golden X слагаемым `+0..3` наряду с buy-tier, трендом,
дивергенцией и объёмом (`golden_x/classifier.signalScore`) и отображается бейджем
в уведомлении.

## Конфигурация

Все пороги — в `rank.Config` / `rank.DefaultConfig()`
(`internal/service/screener/dividend/rank/config.go`). Это единая точка
калибровки; логика (`rank.go`) от значений не зависит. Сервис использует
`DefaultConfig()`, кэш-TTL и размер топа задаются опциями
(`defaultTTL = 24h`, `defaultTopN = 25`).

## Осознанные ограничения

- **Missing net debt → оптимистичный Safety.** `leverageScore(0) = 0.9`: имя с
  невыгруженным (0) `NetDebt/EBITDA` получает почти максимум пилляра Safety.
  Для банков метрика неприменима, а yield-trap gate всё ещё ловит
  `NetDebt/EBITDA > 3` у имён с **присутствующим** долгом. Отличить «нет данных»
  от «реального нуля» на proto3-поле нельзя, а нейтрализация `0 → 0.5` штрафовала
  бы легитимные компании с реально низким долгом — риск оставлен осознанно.
- `indicators.Percentile` (R-7 интерполяция) ядром не используется — только
  `PercentileRank`.
- **`FreeFloat == 0` → отсев.** Как и `MarketCapitalization == 0`, ноль в
  free-float трактуется как неликвид и отсеивает имя. Это может задеть
  легитимное ликвидное имя с дырой в данных (напр. OZON приходит с float 0),
  но такие имена и так с бонусом 0 и внизу списка; альтернатива (пропускать 0)
  вернула бы неторгуемые имена вроде Удмуртнефти в топ. Риск оставлен осознанно.
