# VWAP-возврат (`vwap_rev`, 30m, лонг)

Дизайн: `docs/superpowers/specs/2026-07-28-vwap-reversion-design.md`
Код: `internal/service/trading_strategy/vwap_rev/strategy/core`

Backtest-only стратегия: живого раннера нет, только `cmd/backtest -strategy vwap_rev`.

## Индикатор

`VWAP` и `σ` (объёмно-взвешенное СКО типичной цены вокруг VWAP) считаются функцией
`pkg/indicators.SessionVWAP` заново на каждом баре из окна свечей — межбарного состояния нет.

- **Якорь — первый бар календарного дня МСК**, а не открытие основной сессии: тонкие утренние
  бары весят по объёму почти ноль, поэтому взвешивание отсекает их само.
- **Первая сессия в окне всегда считается неполной** (`barsFromOpen = -1` на всех её барах),
  безусловно — даже если окно случайно начинается ровно с открытия дня. Скользящее окно почти
  всегда начинается с середины дня, и VWAP такой сессии посчитан от произвольной точки; текущий
  бар всегда принадлежит последней сессии окна, так что на сигналы это правило не влияет, но
  без него стратегия торговала бы по мусорному якорю.

## Правила

**Вход** (лонг, только когда позиции нет; все условия обязательны):

1. `barsFromOpen ≥ MinBarsFromOpen` — на первых барах дня σ ещё бессмысленна, утренняя сессия
   неликвидна. Единственная ручка «как рано начинаем торговать».
2. `Close ≤ VWAP − EntryK·σ` — цена дёшева относительно сессионного консенсуса.
3. `Close ≥ VWAP − MaxDevK·σ` — отсечка «это обвал, а не откат». `MaxDevK ≤ 0` выключает
   правило.
4. `(VWAP − Close) / Close · 100 ≥ MinEdgePct` — **главный гейт против торговли внутри
   издержек**: ход до цели обязан окупать 0.1% комиссии за круг с запасом.
5. `Close ≥ Low + MinClosePos·(High − Low)` — бар закрылся не в нижней части своего диапазона,
   не ловим нож. `MinClosePos ≤ 0` выключает правило.
6. При `UseDailyTrend = 1`: `Close > EMA(DailyEMAPeriod)` по дневным свечам (`DailyCloses`).
   Гейт **фейлится закрыто**: при включённом фильтре и недостаточных/отсутствующих дневных
   данных вход запрещается, а не разрешается. `UseDailyTrend = 0` выключает правило.
7. Окно входа: `SessionStartMin`–`SessionEndMin` МСК (07:00–18:00), пятница — до
   `FridayEndMin` (14:00). Нижнюю границу фактически задаёт `MinBarsFromOpen` (п. 1).

**Выходы**, в порядке приоритета (SL проверяется раньше TP: внутрибарный порядок неизвестен,
считаем по худшему сценарию):

1. `SL` — `Low ≤ вход − StopATR·ATR`. Заполнение по стоп-цене с поправкой на гэп вниз
   (`min(stop, open)`). `StopATR = 0` выключает стоп.
2. `TP` — `High ≥ VWAP предыдущего бара`. Заполнение по `max(цель, open)`. Цель берётся с
   **предыдущего** бара — это настоящая лимитная заявка, известная до начала текущего бара, без
   подглядывания в будущее.
3. `TIME` — число закрытых баров с момента входа достигло `MaxHoldBars` → выход по close.
   Возврат, не случившийся за это время, скорее всего не случится. `MaxHoldBars ≤ 0` выключает
   правило.
4. `EOD` — последний бар перед `DayEndMin` (23:00 МСК) → выход по close. Позиция никогда не
   переносится через ночь.

## Параметры

| Поле | Дефолт | Единица | В сетке |
|---|---|---|---|
| `EntryK` | 1.5 | множитель σ | да |
| `MaxDevK` | 4.0 | множитель σ | да (`0` = выкл) |
| `MinEdgePct` | 0.35 | **проценты** (0.35 = 0.35%) | да |
| `MinBarsFromOpen` | 6 | баров с открытия дня | да |
| `MinClosePos` | 0.33 | **доля 0..1** диапазона бара | да (`0` = выкл) |
| `UseDailyTrend` | 1 | 0/1 флаг | да (`0` = выкл) |
| `DailyEMAPeriod` | 50 | дней | да |
| `StopATR` | 1.2 | множитель ATR | да |
| `ATRPeriod` | 14 | баров | нет |
| `MaxHoldBars` | 8 | баров (4 часа на 30m) | да (`0` = выкл) |
| `SessionStartMin` | 420 (07:00 МСК) | минуты от полуночи МСК | нет |
| `SessionEndMin` | 1080 (18:00 МСК) | минуты от полуночи МСК | нет |
| `FridayEndMin` | 840 (14:00 МСК) | минуты от полуночи МСК | нет |
| `DayEndMin` | 1380 (23:00 МСК) | минуты от полуночи МСК | нет |

`StopATR` поддерживает выключение стопа (`StopATR = 0` в ядре, см. `core.go`), но risk-фаза
сетки (`data/params/vwap_rev/grid.json`) перебирает только множители `[0.8, 1.2, 1.6, 2.0]` —
`0` там намеренно нет. Калибровка не должна иметь возможность выбрать вариант «без стоп-лосса»:
это сознательное ограничение сетки, а не пропуск.

## Таймфрейм

Референсный таймфрейм — **30 минут** (`-interval Minutes30`); правила timeframe-agnostic,
длину бара стратегия выводит из данных (`Times`). `Lookback()` = `max(300, 2·ATRPeriod + 20)` —
пол в 300 баров гарантирует, что открытие текущего дня лежит внутри окна. **Ниже 15-минутного
таймфрейма этого пола не хватает**: на 5m/1m барах 300 баров не покрывают две полные сессии, и
`SessionVWAP` не прогреется до конца окна — стратегия для таких таймфреймов не предназначена.

## Запуск

Разведочный прогон на дефолтах:

```
# разведочный прогон на дефолтах
go run ./cmd/backtest -ticker GAZP -strategy vwap_rev -interval Minutes30 \
  -out ./reports/GAZP_vwap -months 24
```

Диагностика одного бара (учитывает `-params`, если он задан):

```
# диагностика одного бара
go run ./cmd/backtest -ticker GAZP -strategy vwap_rev -interval Minutes30 \
  -months 24 -explain "2026-05-14 14:30"
```

Калибровка walk-forward — единственный источник вердикта, in-sample лучший результат не
считается:

```
# калибровка walk-forward (единственный источник вердикта)
go run ./cmd/backtest -ticker GAZP -strategy vwap_rev -interval Minutes30 \
  -calibrate data/params/vwap_rev/grid.json -out ./reports/GAZP_vwap \
  -months 24 -train-months 12 -test-months 3 -metric profit_factor -min-trades 40
```

Грид `data/params/vwap_rev/grid.json`: фазы `entry` (`EntryK` × `MinEdgePct`), `context`
(`UseDailyTrend` × `DailyEMAPeriod`), `quality` (`MaxDevK` × `MinClosePos`), `risk`
(`StopATR`), `hold` (`MaxHoldBars`), `timing` (`MinBarsFromOpen`).
`12 + 4×6 + 4×9 + 4×4 + 4×5 + 4×4 = 124` комбинации. В каждой фазе с опциональным фильтром
есть контрольная точка «выключено» (`MaxDevK=0`, `MinClosePos=0`, `UseDailyTrend=0`,
`MaxHoldBars=0`), совпадающая с ситуацией «фильтра нет», — так базовая версия без фильтров
участвует в сравнении наравне, а не проигрывает по умолчанию. Границы сессии, `DayEndMin` и
сама цель на VWAP в сетку намеренно не входят — это тезис стратегии, а не ручка калибровки.

## Критерии приёмки

Все шесть одновременно, по pooled OOS из rolling walk-forward. Никогда по in-sample лучшему.

1. pooled OOS **PF ≥ 1.5**
2. **≥ 150 OOS-сделок**
3. **win rate ≥ 55%** — профильное требование: ниже — значит это не «стабильный мелкий доход»,
   а обычный RR-трейдинг под другим именем
4. **средняя чистая сделка ≥ +0.15%** — доказательство, что издержки не съели edge
5. **≥ 3 из 4 фолдов с OOS PF > 1.0**
6. `EntryK` и `MinEdgePct` между фолдами гуляют не более чем на один шаг сетки

**Критерий смерти.** Если хоть один из шести пунктов не выполнен — стратегия закрывается и в
live не идёт. Не расширяем сетку, не добавляем седьмой фильтр, не перебираем тикеры в поисках
того, где сработало.

## Результаты калибровки (2026-07-28)

**Вердикт: стратегия закрыта.** Все шесть критериев приёмки провалены на pooled OOS. В live
не идёт, `data/params/vwap_rev/gazp_cal.json` не создан, сетка не расширяется, седьмой фильтр
не добавляется, другие тикеры в поисках рабочей комбинации не перебираются.

### Разведочный прогон (частота сетапа)

```
go run ./cmd/backtest -ticker GAZP -strategy vwap_rev -interval Minutes30 \
  -out ./reports/GAZP_vwap -months 24
```

Результат: **70 сделок** за 24 месяца на дефолтных параметрах (win rate 50.00%, PF 0.723,
чистый PnL −5.15%) — против плановых ≥ 200. Посылка «частота вместо размера» не выполняется
уже на разведочном прогоне.

Разобрано через поочерёдное отключение гейтов (`-params` с одним изменённым полем,
дефолты `data/params/vwap_rev/grid.json`, тот же прогон 24 мес, тот же тикер):

| Вариант | Сделок | Δ к базе (70) |
|---|---|---|
| база (все гейты по дефолту) | 70 | — |
| `MaxDevK=0` (гейт и так не срабатывал при дефолте 4.0) | 70 | 0% |
| `MinBarsFromOpen=0` | 73 | +4% |
| `MinEdgePct=0` | 99 | +41% |
| `EntryK=1.0` (вместо 1.5) | 152 | +117% |
| `MinClosePos=0` | 179 | +156% |
| `UseDailyTrend=0` | 185 | +164% |
| `MinClosePos=0` **и** `UseDailyTrend=0` вместе | 501 | +616% |

Вывод: два доминирующих гейта частоты — `UseDailyTrend` (дневной EMA-фильтр, fail-closed) и
`MinClosePos` (фильтр «не в нижней части бара»), каждый примерно утраивает число сделок при
отключении, а вместе дают 7-кратный рост. `EntryK` (глубина отката в σ) тоже существенно режет.
`MinEdgePct` и `MinBarsFromOpen` — второстепенные ручки. Но даже сняв оба доминирующих гейта
разом, база остаётся кратно ниже 200 при дефолтных остальных параметрах — сетап на GAZP/30m в
принципе редкий, а не просто пережатый одним фильтром. Сама сетка это подтвердила: даже её
самые мягкие комбинации (см. ниже) не вытянули OOS-сделки к плановым числам.

### Walk-forward калибровка

```
go run ./cmd/backtest -ticker GAZP -strategy vwap_rev -interval Minutes30 \
  -calibrate data/params/vwap_rev/grid.json -out ./reports/GAZP_vwap \
  -months 24 -train-months 12 -test-months 3 -metric profit_factor -min-trades 40
```

Отчёт: `reports/GAZP_vwap/GAZP_vwap_rev_Minutes30_20260728_115647_walkforward.md` (4 фолда,
train 12 мес / test 3 мес, шаг 3 мес).

Пул OOS: 45 сделок, 17 выигрышных / 28 проигрышных, win rate 37.78%, PF 0.416, gross profit/loss
5374.74 / 12914.40, expectancy −167.55, compounded return −7.40%.

| 2 | 2024-10-28—2025-10-28 | 2025-10-28—2026-01-28 | 1.384 | 0.729 | 13 |

### Шесть критериев приёмки — факт

| # | Критерий | Порог | Факт | Пройден |
|---|---|---|---|---|
| 1 | pooled OOS profit factor | ≥ 1.5 | **0.416** | Нет |
| 2 | OOS-сделок | ≥ 150 | **45** | Нет |
| 3 | win rate по пулу OOS | ≥ 55% | **37.78%** | Нет |
| 4 | средняя чистая сделка | ≥ +0.15% | **≈ −0.17%** (см. методику ниже) | Нет |
| 5 | фолдов с OOS PF > 1.0 | ≥ 3 из 4 | **0 из 4** (0.413 / 0.729 / 0.264 / 0.000) | Нет |
| 6 | разброс `EntryK`/`MinEdgePct` между фолдами | ≤ 1 шаг сетки | `EntryK`: 1 шаг (1.5→1.0); `MinEdgePct`: **2 шага** (0.25→0.5 при сетке 0.25/0.35/0.5) | Нет |

Методика критерия 4: markdown walk-forward отчёт не печатает среднюю % сделку по пулу (только
сумму PnL и compounded return по фолдам). Значение пересчитано отдельным прогоном той же
`svc.RunWalkForward` — те же кандидаты, тот же грид, тот же тикер, — который для каждого фолда
проигрывает победивший из `WinnerParams` набор параметров на окне train+test и оставляет только
сделки, вошедшие в OOS-окно (то же правило `tradesEnteredFrom`), затем усредняет `Trade.PnLPct`
по объединённому пулу. Из-за того что `-months` считается от `time.Now()`, а пересчёт выполнялся
на несколько минут позже официального прогона, границы фолдов сдвинулись на эту же дельту:
пересчёт дал 44 сделки вместо 45 (расхождение на 1 сделку в фолде 3 — 21 вместо 22, у самой
границы окна), PF 0.414 вместо 0.416, win rate 36.36% вместо 37.78%. Совпадение почти точное
подтверждает, что метод воспроизводит официальный прогон; средняя чистая сделка по этому
пересчитанному пулу (n=44) — **−0.1723%**. Расхождение в один пограничный трейд не меняет ни
знака, ни порядка величины — критерий 4 провален с большим запасом при любой из двух версий пула.

### Два факта, которые и есть ценность отрицательного результата

**(а) Частота.** Разведочный прогон на дефолтах дал 70 сделок за 24 месяца против плановых 200 —
посылка «частота вместо размера» не подтвердилась ещё на старте. Гейт-абляция (таблица выше)
показывает, что `UseDailyTrend` и `MinClosePos` — два основных ограничителя частоты (каждый
самостоятельно почти утраивает число сделок, вместе — почти в 8 раз), `EntryK` тоже существен, но
даже сняв оба главных фильтра, база остаётся далеко от 200: редкость встроена в саму геометрию
сетапа (глубокий откат от VWAP на 30m), а не в один избыточный фильтр.

**(b) Подгонка, а не edge.** In-sample PF во всех четырёх фолдах (1.118 / 1.384 / 1.279 / 0.934)
выше соответствующего OOS PF (0.413 / 0.729 / 0.264 / 0.000) в 2–4 раза, а в четвёртом фолде
даже in-sample PF < 1 (0.934) — калибратор не нашёл на своём train-окне ни одной прибыльной по
всей сетке комбинации, и лучшая из убыточных не дала на OOS ни одной сделки. Это классическая
картина подгонки под шум train-окна, а не наличие устойчивого edge.

### Бонус-чек переносимости

Не выполнялся: приёмка провалена по всем шести пунктам с большим запасом (PF 0.416 против
порога 1.5, 45 сделок против 150), бонус-чек существует для случая «формально прошли, но
настораживает», который здесь не наступает — прогон на NVTK/RUAL ничего не добавил бы к
вердикту.
