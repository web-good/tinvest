## Конфигурация

Вся конфигурация задаётся через переменные окружения. Для каждой есть значение по
умолчанию; чтобы переопределить — задайте env-переменную перед запуском приложения.

### Переменные окружения

| Переменная | По умолчанию | Описание |
|----------|---------|-------------|
| `REVERSION_ACCOUNT_ID` | *обязательная* | ID отдельного брокерского счёта для стратегии reversion. Должен быть валидным счётом Tinkoff Invest. |
| `REVERSION_TOKEN` | *обязательная* | API-токен Tinkoff Invest для стратегии reversion. Аутентифицирует **отдельный** gRPC-клиент reversion (не общий `T_BANK`). Секрет — задавайте в рантайме, не коммитьте. Нужен, когда счёт reversion под отдельным логином Tinkoff. |
| `REVERSION_TICKERS` | `UGLD,EUTR,NVTK` | Список тикеров боевого набора через запятую. См. [Набор тикеров](#набор-тикеров) — зарегистрированные тикеры и ограничения. |
| `REVERSION_BUY_PCT` | `10` | Размер позиции в процентах от полной стоимости счёта (кэш + открытые позиции). Например, `10` означает, что каждая покупка нацелена на 10% текущей стоимости счёта. |
| `REVERSION_TRADE_ENABLED` | `false` | **Критично:** если `false`, ордера не выставляются — только логи и уведомления (бумажный режим). Ставьте `true` только в проде после полного тестирования. |
| `REVERSION_NOTIFY_ENABLED` | `true` | Если `true`, входы, выходы, пропуски и ошибки публикуются в Telegram. Поставьте `false` для «тихой» работы. |

**Пример `env/local.env`:**

```bash
REVERSION_ACCOUNT_ID=your_account_id_here
REVERSION_TICKERS=UGLD,EUTR,NVTK
REVERSION_BUY_PCT=10
REVERSION_TRADE_ENABLED=false
REVERSION_NOTIFY_ENABLED=true
```

## Матрица флагов

Флаги `TRADE_ENABLED` и `NOTIFY_ENABLED` независимы. Выберите свой режим:

| `TRADE_ENABLED` | `NOTIFY_ENABLED` | Поведение |
|---|---|---|
| `false` | `true` | **Бумажный режим:** сигналы публикуются только в Telegram; ордера у брокера не выставляются. Для разработки и тестирования. |
| `true` | `true` | **Боевая торговля + уведомления:** ордера выставляются, полная отчётность в Telegram. Продакшн-режим. |
| `true` | `false` | **Боевая торговля, тихо:** ордера выставляются, вывода в Telegram нет. Если уведомления обрабатываются где-то ещё. |
| `false` | `false` | **Холостой прогон (dry run):** ни ордеров, ни уведомлений; только вывод в лог. Для отладки и сбора метрик. |

### Рекомендуемый порядок

1. **Разработка:** `TRADE_ENABLED=false`, `NOTIFY_ENABLED=true` (бумажный режим в Telegram).
2. **Тестирование:** `TRADE_ENABLED=false`, `NOTIFY_ENABLED=false` (холостой прогон только в логи).
3. **Бой:** `TRADE_ENABLED=true`, `NOTIFY_ENABLED=true` (полная работа с алертами).

## Расписание запуска

Runner reversion выполняет две независимые cron-задачи:

### Расписание buy-pass

**Cron:** `0 7-23 * * 1-5`
**Время:** 07:00, 08:00, …, 23:00 по Москве, понедельник–пятница
**Действие:** по каждому тикеру без открытой позиции вычислить сигналы входа и выставить ордера на покупку, если сигнал сработал.

### Расписание manage-pass

**Cron:** `0 7-23,0 * * *`
**Время:** 07:00, 08:00, …, 23:00, 00:00 по Москве, ежедневно (без пропуска 01:00–06:00)
**Действие:** по каждому тикеру с открытой позицией вычислить сигналы выхода и выставить ордера на продажу, если сигнал сработал.

Оба прохода работают в продакшн-режиме (`APP_ENV=prod`). В режиме разработки
(`APP_ENV=dev`) воркеры запускаются параллельно как горутины без задержки расписания.

## Управление состоянием

### Файл состояния

Runner сохраняет per-ticker entry-state в локальном JSON-файле:

**Путь:** `data/state/reversion_<REVERSION_ACCOUNT_ID>.json`

**Формат:** объект с ключами-тикерами, в каждом:

```json
{
  "NVTK": {
    "ticker": "NVTK",
    "entryTime": "2026-06-26T09:00:00Z",
    "entryPrice": 2845.5,
    "entryATR": 12.3,
    "maxFav": 2857.8,
    "quantity": 10,
    "stopOrderId": "b3e1c4a0-...-uuid",
    "stopPrice": 2833.2,
    "stopReason": "TRAIL"
  },
  "UGLD": {
    "ticker": "UGLD",
    "entryTime": "2026-06-26T10:00:00Z",
    "entryPrice": 1234.25,
    "entryATR": 8.5,
    "maxFav": 1234.25,
    "quantity": 50,
    "stopOrderId": "",
    "stopPrice": 0,
    "stopReason": ""
  }
}
```

`NVTK` — интрабарный тикер (`UseIntrabarStop=1`): стоп-поля заполнены реальной биржевой
заявкой. `UGLD` — close-тикер (`UseIntrabarStop=0`, дефолт): стоп-поля остаются пустыми/
нулевыми **всю жизнь позиции** — биржевая заявка для него не выставляется никогда (см.
[«Стоп-заявки»](#стоп-заявки) ниже). То же верно для `EUTR`.

**Поля:**

- `ticker` — код инструмента (например, `UGLD`).
- `entryTime` — UTC-метка времени ордера на покупку (когда позиция была открыта).
- `entryPrice` — средняя цена исполнения ордера на покупку.
- `entryATR` — значение ATR на момент входа; используется логикой выхода для расчёта стопов, трейлинга и breakeven. **Брокер его не отдаёт — поэтому храним сами.**
- `maxFav` — максимальная благоприятная цена, достигнутая с момента входа; монотонно поднимается на каждом тике manage-pass (нужна для trailing-stop и breakeven).
- `quantity` — количество **штук** в позиции (не лотов).
- `stopOrderId` — ID активной биржевой стоп-заявки (`""`, если сейчас нет заявки на бирже —
  например, dry-run, временный провал `Place`, **или тикер на close-модели**, где заявка не
  выставляется вовсе).
- `stopPrice` — уровень, на который выставлена (или должна быть выставлена — в dry-run тоже
  обновляется) текущая стоп-заявка. Заполняется только у тикеров с `UseIntrabarStop=1`; у
  close-тикеров остаётся `0` всю жизнь позиции.
- `stopReason` — компонент уровня STOP, который сейчас связывает заявку: `SL` / `ATRSL` /
  `TRAIL`. Подробности каждого — в `strategy.md`. Как и `stopPrice`, заполняется только у
  тикеров с `UseIntrabarStop=1`; у close-тикеров остаётся пустым.

Эти три поля — часть контракта только интрабарной модели (`UseIntrabarStop=1`); у
close-тикеров (`UseIntrabarStop=0`, сейчас UGLD/EUTR) они не используются: выход по STOP
опирается на тот же расчёт `core.DesiredStop` от `entryPrice`/`entryATR`/`maxFav`, что и
для интрабарных тикеров, но пересчитывается заново на каждом manage-тике внутри
`core.Decide`, без отдельной персистентности уровня заявки.

Подробный жизненный цикл `stopOrderId`/`stopPrice`/`stopReason` — в разделе
[«Стоп-заявки»](#стоп-заявки) ниже.

### Атомарная запись

Файлы состояния пишутся атомарно (временный файл + `rename`), чтобы избежать порчи,
если процесс упадёт в середине записи.

### Восстановление (reconstruct)

Если в брокерском счёте позиция есть, а файл состояния отсутствует (например, после
потери файла или восстановления окружения), runner:

1. Запрашивает у брокера сделки по инструменту (`GetInstrumentTrades`, за последние 120 дней).
2. Находит **последнюю** BUY-сделку по этому тикеру → `entryTime`.
3. Берёт `entryPrice` из средней цены покупки брокера, а `quantity` — из текущей позиции портфеля.
4. Пересчитывает `entryATR`, загружая исторические часовые свечи вокруг входа и прогоняя индикатор ATR на окне, заканчивающемся на баре входа.
5. Вычисляет `maxFav` как максимум close с момента входа.
6. Сохраняет восстановленное состояние на диск.
7. Шлёт алерт в Telegram: `"⚠️ Reversion UGLD — стейт восстановлен из API: вход 2845.5000, ATR 12.3000"`.

Это позволяет runner'у продолжить работу без ручного вмешательства, а оператор
получает уведомление о восстановлении. Восстановленные значения (особенно ATR)
приблизительны, поэтому алерт обязателен.

## Стоп-заявки

Компонента STOP стратегии (`SL`/`ATRSL`/`TRAIL` — см. `strategy.md`) в live моделируется
**одной биржевой стоп-market-заявкой на продажу** (GTC), а не проверкой сигнала на каждом
тике — но только у тикеров с `UseIntrabarStop=1` (интрабарная модель, см. `strategy.md` →
«Модель исполнения стопов»; сейчас это только NVTK). Пакет:
`internal/service/trading_strategy/reversion/live/stoporders`.

### Область действия: только интрабарные тикеры

Для тикеров на close-модели (`UseIntrabarStop=0`, дефолт; сейчас UGLD и EUTR) весь
механизм ниже (постановка/синхронизация/детект срабатывания) не выполняется:

- `placeInitialStop` делает ранний return сразу после проверки `p.UseIntrabarStop != 1` —
  заявка после входа не выставляется.
- Блок синхронизации в `managePass` для такого тикера не запускается вовсе.
- Выход по STOP исполняется как обычная рыночная продажа сразу после того, как
  `core.Decide` увидел `close ≤ уровень` на очередном часовом тике — тем же путём, что и
  остальные close-based сигналы (`OB`/`RSI50`/`BE`/`RSIOS`/`EMAX`, см. «Правило "cancel
  перед любой рыночной продажей"» ниже; для close-тикера отменять там обычно нечего, так
  как активной заявки нет).

**Переключение тикера с интрабара на close-модель:** если в стейте тикера остался
непустой `StopOrderID` (заявка, оставшаяся после того, как `UseIntrabarStop` в его пакете
сменили с `1` на `0`), ближайший `managePass`, у которого `List` доступен, это
обнаруживает и чистит: если заявка ещё жива на бирже — сначала `Cancel`, затем очистка
`StopOrderID`/`StopPrice`/`StopReason` в стейте; если заявки уже нет среди активных —
поля просто очищаются без вызова `Cancel`. Провал `Cancel` — алерт, стейт в этом тике не
трогается, ретрай на следующем часовом тике. Если `List` недоступен в этом тике — очистка
откладывается до следующего прохода (симметрично общему правилу «`List` недоступен» из
раздела «Детект срабатывания стопа» ниже). Повторного выставления заявки для close-тикера
при этом не происходит — обратный переход её просто не ставит.

### Постановка сразу после входа

Сразу после фактического исполнения покупки (`buy.go`, `placeInitialStop`) runner считает
`core.DesiredStop(params, entryPrice, entryATR, maxFav)` и, если хоть одна компонента STOP
включена, тут же выставляет стоп-заявку на весь купленный объём. Цель — не оставлять позицию
без защиты до первого часового manage-тика. Провал выставления не откатывает покупку: `entry`
сохраняется с пустым `stopOrderId`, а следующий manage-pass довыставит заявку по общей логике
синхронизации ниже.

### Часовая синхронизация (manage-pass)

На каждом manage-тике по каждой позиции с открытым `stopOrderId`:

1. **Один вызов `List`** на весь проход (`GetStopOrders`) — снимок активных заявок счёта,
   индексированный и по `StopOrderID`, и по инструменту.
2. Если своя заявка пропала из снимка (`stopOrderId` есть в state, но не в списке биржи) —
   это может значить, что она сработала (см. «Детект срабатывания» ниже) или потерялась;
   runner сбрасывает `stopOrderId` и перевыставляет.
3. Если заявки нет в state, а на бирже висит чужая/устаревшая заявка на этот инструмент
   (например, после `reconstruct`) — она отменяется (`Cancel`). **Если `Cancel` падает —
   новая заявка в этом тике НЕ ставится** (алерт вместо этого): stray-заявка всё ещё жива и
   продолжает защищать позицию, а постановка второй означало бы два живых SELL-стопа на
   один инструмент — при касании уровня второй продал бы уже не имеющиеся бумаги (шорт на
   марже). Повтор снятия — на следующем часовом тике.
4. Желаемый уровень пересчитывается **от обновлённого `MaxFav`** (после того как maxFav
   поднят по текущему закрытию).
5. **Реконсиляция размера:** если `stopOrderId` есть и жив, но его `Lots` не совпадают с
   текущими лотами позиции (`entry.Quantity / sh.Lot`) — принудительный `Cancel` + `Place` на
   актуальный объём, **даже если уровень цены не поднялся**. Оверсайз на бирже опаснее не
   вовремя подтянутого трейла, поэтому эта проверка идёт раньше сравнения уровней.
6. Иначе заявка перевыставляется, только если желаемый уровень **вырос** (`level >
   entry.StopPrice`) — трейлинг только подтягивается вверх, никогда не опускается.
7. И в 5, и в 6 перевыставление — это `Cancel` старой заявки, затем `Place` новой на новый
   уровень/объём. Если `Cancel` падает — алерт в Telegram, **старая заявка не трогается** и
   продолжает защищать позицию; повтор попытки — на следующем часовом тике.

### Детект срабатывания стопа

Если позиция пропала из портфеля брокера (`held[sh.ID]` не найден), а в state тикер всё ещё
числится с непустым `stopOrderId` — runner различает сработавший стоп от ручной продажи
по тому же снимку `List` (`GetStopOrders`), что взят один раз в начале прохода:

- **Заявки `stopOrderId` больше нет в списке активных** — сработала именно она: runner шлёт
  `notifier.Exit` с **сохранёнными** `stopPrice`/`stopReason` (а не пересчитанными заново) и
  удаляет запись из state.
- **Заявка `stopOrderId` всё ещё живая на бирже** — позицию продали НЕ через наш стоп
  (например, вручную в приложении брокера); наша GTC-заявка иначе осиротела бы навсегда и
  при будущем входе по этому тикеру продала бы новую позицию. Runner отменяет её
  (`Cancel`) и шлёт алерт «позиция продана вне раннера, снял осиротевший стоп» — **без**
  `notifier.Exit` (это не сработавший стоп). Если `Cancel` падает — алерт об ошибке, state
  **не чистится**, ретрай на следующем часовом тике.
- **`List` недоступен (`listErr != nil`)** — runner не может отличить один случай от
  другого: консервативно шлёт алерт и оставляет state как есть до следующего прохода, а не
  выдумывает `Exit` вслепую.
- Если `stopOrderId` в state пуст — просто чистится запись, присматривать не за чем.

У тикеров на close-модели (`UseIntrabarStop=0`) `stopOrderId` пуст всегда, так что это
детектирование их вообще не касается: их собственный выход по STOP уже прошёл через
обычный путь `SignalSell` → `notifier.Exit` в том же manage-тике, где ядро увидело
`close ≤ уровень`, и запись из state к моменту этой проверки уже удалена.

### Правило «cancel перед любой рыночной продажей»

Когда ядро (`core.Decide`) возвращает `SignalSell` по **любой** причине (`OB`, `RSI50`, `BE`,
`RSIOS`, `EMAX` — и даже сам `STOP`, если он же обнаружен close-путём на этом тике), runner
сначала снимает активную стоп-заявку (`Cancel`) и только потом шлёт рыночный ордер на
продажу. **Если `Cancel` падает — рыночная продажа в этом тике не выставляется**: без снятия
биржевой стоп-заявки продать значило бы рискнуть двойной продажей (рыночный ордер +
случайное срабатывание старого стопа). Алерт в Telegram, retry на следующем тике.

### Частичное исполнение

Если биржа исполнила стоп-заявку не полностью (редкий случай для ликвидных бумаг набора),
runner видит `pos.Quantity < entry.Quantity` на следующем тике. Поведение — **bookkeeping-only**:
`Quantity` в state уменьшается до фактического остатка и шлётся алерт; `stopOrderId` **не
трогается и не отменяется** этим шагом (снимок `List` для этого тика уже сделан один раз в
начале прохода — повторная отмена той же заявки дала бы ложный alert о двойном cancel).
Реконсиляция размера **живой** заявки на новый (уменьшенный) `entry.Quantity` происходит по
общему пути синхронизации выше — шаг 5 (реконсиляция размера) сработает на этом же или
следующем тике, потому что `Lots` заявки на бирже теперь не совпадают с новыми лотами
позиции.

### Dry-run (`REVERSION_TRADE_ENABLED=false`)

`stoporders.Executor` использует тот же флаг `TradeEnabled`, что и обычный `executor`
рыночных ордеров (единой на всё — отдельного тумблера для стоп-заявок нет). В dry-run:

- `Place` не обращается к API и возвращает `Result{Placed: false}` — `stopOrderId` в state
  остаётся пустым, но `stopPrice`/`stopReason` **всё равно обновляются**, чтобы бумажное
  состояние отражало, какой уровень **был бы** выставлен на бирже;
- `Cancel` и `List` — no-op (`List` возвращает `nil, nil`, так что синхронизация с биржей
  просто не выполняется — нечего сверять);
- уведомление `notifier.StopSet` получает пометку «БУМАЖНАЯ сделка» так же, как `Entry`/`Exit`.

### Бэкстоп через проверку ядра (тикеры на интрабарной модели)

Это касается только тикеров с `UseIntrabarStop=1`. Помимо резидентной биржевой заявки,
каждый manage-тик заново вызывает `core.Decide` на последней закрытой часовой свече — и он
**тоже** проверяет условие STOP, но своим, интрабарным триггером (`low` бара ≤ уровню).
Если по какой-то причине биржевая заявка не сработала вовремя, пропущена или её вообще нет
(dry-run, временный провал `Place`), но цена всё равно ушла ниже уровня, ядро на следующем
часовом тике само вернёт `SignalSell` с причиной `SL`/`ATRSL`/`TRAIL`, и runner продаст
рыночным ордером по общему пути «cancel перед любой рыночной продажей» (см. выше). Это
резервный контур: он реагирует не быстрее часового расписания, но гарантирует, что
защитный выход в конце концов сработает даже без живой биржевой заявки.

У тикеров на close-модели (`UseIntrabarStop=0`) отдельного «бэкстопа» нет и не нужно:
проверка `core.Decide` (по close, а не по low) — это **единственный** механизм STOP, а не
резерв поверх биржевой заявки, которой для этих тикеров попросту не существует.

## Размер позиции

Каждый ордер на покупку нацелен на `REVERSION_BUY_PCT`% от **полной стоимости счёта**
(кэш + открытые позиции по рыночной оценке).

**Расчёт:**

1. Получить полную стоимость счёта (кэш + оценка позиций) от брокера.
2. Вычислить целевую сумму: `accountValue × BUY_PCT / 100`.
3. Получить текущую цену акции и размер лота (1 для большинства акций Tinkoff Invest).
4. Вычислить количество в лотах: `floor(targetAmount / (price × lotSize))`.
5. Дополнительно ограничить доступным кэшом: `min(lots, floor(cash / lotCost))`.
6. Если `quantity == 0` или кэша не хватает на лот → пропуск ордера + алерт.

**Пример:**

- Стоимость счёта: 1 000 000 рублей.
- `REVERSION_BUY_PCT=10` → цель: 100 000 рублей.
- Цена UGLD: 2 800 рублей, размер лота: 1.
- Количество: `floor(100 000 / 2 800) = 35 лотов`.
- Доступный кэш: 150 000 рублей → достаточно, ордер выставляется.

Если доступного кэша меньше целевой суммы → ордер пропускается, шлётся алерт в Telegram.

> **Отличие от бэктеста:** в бэктесте дефолт `Fraction=1.0` = **100% кэша** на одну
> позицию (так считались PF по отдельному тикеру). В live дефолт `BUY_PCT=10` —
> **10% от счёта**, и тикеры делят общий капитал.

## Ограничения по позициям

- **Одна позиция на тикер:** несколько входов в один тикер не допускаются. Пока позиция есть, новая покупка не выставляется, пока она не будет продана.
- **Тикеры вне набора:** позиции по тикерам, которых нет в `REVERSION_TICKERS`, не трогаются (вне зоны ответственности runner'а reversion).

## Выставление ордеров

### Тип ордера

Только рыночные ордера (`ORDER_TYPE_MARKET`). Исполняются по лучшей доступной
рыночной цене на момент выполнения.

### Идемпотентность

Каждому ордеру присваивается уникальный UUID (`order_id`) для идемпотентности. Если
тот же ордер будет повторён (например, из-за сетевого таймаута), брокер распознает
дубликат `order_id` и не исполнит его дважды.

### Обработка отказов

Если брокер отклоняет ордер (рынок закрыт, недостаточно средств, неверный инструмент):

1. Состояние не записывается (ни вход, ни подтверждение продажи).
2. Ошибка логируется.
3. При `NOTIFY_ENABLED=true` шлётся алерт в Telegram.
4. Runner повторяет попытку на следующем тике расписания.

### Учёт исполнения

Runner записывает фактическую цену и количество исполнения, которые сообщил брокер.
Если количество отличается от запрошенного (исключительный случай частичного
исполнения), в состоянии сохраняется фактически исполненное количество.

## Известные расхождения с бэктестом

Live-runner даёт другие исполнения, чем бэктест, из-за неизбежных ограничений
реального времени:

### Время исполнения входа

- **Бэктест:** исполняет вход по **close того бара, на котором сработал сигнал** (close той же свечи).
- **Live:** просыпается в **начале следующего часа** и выставляет рыночный ордер, который исполняется около **open следующего бара** (смещение ~1 бар + проскальзывание).

На ликвидных бумагах (UGLD, EUTR) разрыв обычно мал. На менее ликвидных тикерах
live-исполнения могут заметнее отклоняться от PnL бэктеста.

### Логика исполнения выхода

- **STOP (`SL`/`ATRSL`/`TRAIL`) у тикеров на интрабарной модели (`UseIntrabarStop=1`,
  сейчас NVTK):**
  - **Бэктест:** интрабарный триггер по `low` бара, гэп-исполнение как
    `min(stopLevel, open)` того же бара — реалистично исполняет на гэпе внутри бара
    (`internal/domain/backtest/engine.go`).
  - **Live:** реальная резидентная биржевая стоп-market-заявка (`live/stoporders`) —
    исполняется биржей, как только цена внутри часа проходит уровень, а не только на
    часовой границе. Это ближе к модели бэктеста, чем остальные выходы, но точная цена
    филла всё равно зависит от биржевой ликвидности/проскальзывания в момент срабатывания,
    а не от гэп-формулы бэктеста.
- **STOP у тикеров на close-модели (`UseIntrabarStop=0`, дефолт; сейчас UGLD, EUTR):**
  - **Бэктест:** триггер по close сигнального бара (`in.price ≤ stopLevel`), филл по close
    — без гэп-протекции `min(level, open)` (сознательное отличие от июньской реализации,
    см. `strategy.md` → «Модель исполнения стопов»).
  - **Live:** биржевой стоп-заявки нет вовсе; обычный рыночный ордер, выставленный в
    момент, когда `core.Decide` увидел `close ≤ stopLevel` на очередном часовом тике — тот
    же путь исполнения, что у остальных close-based выходов ниже.
- **Остальные (`OB`/`RSI50`/`BE`/`RSIOS`/`EMAX`, и `STOP` у close-тикеров — см. выше):**
  - **Бэктест:** исполняются по close сигнального бара.
  - **Live:** обычный рыночный ордер, выставленный в момент, когда `core.Decide` увидел
    сигнал на очередном часовом тике (около open следующего бара, см. «Время исполнения
    входа» выше по аналогии) — эти выходы гэп-математику бэктеста не воспроизводят.

**Влияние:** live-результаты не совпадут с P&L бэктеста точно, особенно на
волатильных/гэповых бумагах. Бэктест — ориентир, а не гарантия.

### Добавление тикера

1. Прогоните walk-forward бэктест по кандидату.
2. Проверьте out-of-sample Profit Factor (PF). Принимайте только если PF > 1.0 и видна стабильная прибыльность по всем тестовым окнам.
3. Добавьте тикер в `REVERSION_TICKERS` в вашем `.env`.
4. Задеплойте и сравнивайте live P&L с прогнозами бэктеста.

## Мониторинг и алерты

### Уведомления в Telegram

При `NOTIFY_ENABLED=true` runner шлёт сообщения о:

- **Вход:** `🟢 Вход UGLD\n  Цена: 2845.5000 | Лотов: 35 | Штук: 35`
- **Выход:** `🔴 Выход UGLD [OB]\n  Цена: 2857.8000 | Штук: 35` (в скобках — код причины:
  `SL`/`ATRSL`/`TRAIL` — компоненты STOP (интрабарные у тикеров с `UseIntrabarStop=1`,
  close-based у остальных — см. `strategy.md` → «Модель исполнения стопов») — плюс
  `OB`/`RSI50`/`BE`/`RSIOS`/`EMAX`, всегда close-based; полный порядок приоритета и
  семантика каждого — в `strategy.md`)
- **Стоп-заявка (пере)выставлена:** `🛡 UGLD: стоп-заявка TRAIL на 2833.2000` — шлётся из
  `replaceStop`/`placeInitialStop`, только когда уровень или причина реально изменились (не
  на каждом тике); см. [«Стоп-заявки»](#стоп-заявки) выше.
- **Пропуск (нехватка кэша/бюджета):** `⏭️ Пропуск EUTR\n  бюджета 100000.00 не хватает на 1 лот (...)`
- **Алерт восстановления:** `⚠️ Reversion UGLD\n  стейт восстановлен из API: вход 2845.5000, ATR 12.3000`
- **Ошибка:** `⚠️ Reversion UGLD\n  ордер на покупку отклонён: market closed`

Сообщения отправляются только при `NOTIFY_ENABLED=true`; в бумажных сделках
добавляется пометка «*(БУМАЖНАЯ сделка, ордер не выставлен)*».

### Логи

Подробные логи выводятся в stdout/stderr. В проде направляйте их в файл или
агрегатор логов.

**Уровни логов:**

- `INFO` — штатные операции (входы, выходы, пропуски).
- `ERROR` — отказы ордеров, ошибки I/O файла состояния, сбои API.
- `DEBUG` — загрузка свечей, расчёт индикаторов, логика решений (только dev-режим).

## Восстановление и краевые случаи

### Рынок закрыт

Если свежей закрытой свечи нет (выходные, вне сессии), manage-pass выполняется, но
не предпринимает действий (фиксируется только переоценка по рынку). Runner не падает;
он ждёт следующего тика расписания.

### Позиция в портфеле, состояние отсутствует

Обрабатывается фолбэком reconstruct (см. [Управление состоянием](#управление-состоянием)).
Алерт уходит в Telegram.

### Расхождение количества с брокером

Если брокер сообщает количество исполнения, отличное от запрошенного, в состоянии
записывается фактическое количество. Это может означать частичное исполнение (редко)
или округление брокером. Проверьте в приложении брокера.

### Ручные изменения позиции

Если вы вручную купите или продадите тикер на счёте вне runner'а, он может не
заметить изменение сразу. Следующий manage-pass проверит портфель брокера. Если
ручная покупка создала позицию, а состояние отсутствует — сработает reconstruct.
Если ручное закрытие убрало позицию, следующий buy-pass попробует новый вход (если
сработает сигнал).

**Лучшая практика:** избегайте ручных сделок на счёте reversion во время боевой работы.

## Диагностика проблем

### Входы не срабатывают

1. Проверьте `REVERSION_TRADE_ENABLED=true` (не бумажный режим).
2. Проверьте уведомления Telegram; если выключены, включите `NOTIFY_ENABLED=true`, чтобы видеть причины пропусков.
3. Прогоните бэктест на том же таймфрейме/данных, чтобы убедиться, что сигнал ожидается.
4. Проверьте логи на ошибки загрузки свечей или расчёта индикаторов.

### Входы срабатывают, но ордера не выставляются

1. Если `TRADE_ENABLED=false`, ордера пропускаются намеренно (бумажный режим).
2. Проверьте доступный кэш. Если расчёт размера даёт 0 лотов, шлётся алерт в Telegram.
3. Проверьте логи на ошибки API брокера (например, «ордер отклонён: market closed»).
4. Убедитесь, что ID счёта в `REVERSION_ACCOUNT_ID` верен и имеет права на торговлю.

### Порча файла состояния

Удалите файл состояния (`data/state/reversion_<account>.json`). На следующем
manage-pass фолбэк reconstruct восстановит его из API брокера.

### Устаревшие данные / нет свечей

Если загрузка свечей падает (ошибка API, сетевой таймаут), логи покажут ошибку.
Runner повторяет на следующем тике. Постоянного кэша свечей нет; каждый тик грузит
свежие данные.
