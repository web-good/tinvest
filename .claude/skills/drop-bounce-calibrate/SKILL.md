# drop_bounce: калибровка тикера на 5m и 15m и выбор таймфрейма

Аргументы: `<TICKER> [заметки владельца]`. Владелец передаёт тикер и ждёт вердикт, а не меню:
сам гоняешь, сам выбираешь, доводишь до пакета тикера и в конце задаёшь не больше одного вопроса.
Механика стратегии — `docs/drop_bounce/strategy.md`. Скрипты — в `scripts/` рядом с этим файлом,
запускай их как `python3 -I .claude/skills/drop-bounce-calibrate/scripts/<script>.py`.

**Нарушить букву правила — значит нарушить его дух.** Каждое правило ниже появилось из реального
провала калибровки drop_bounce.

## 0. Правила каждого прогона

- **Таймфреймы — только Minutes5 и Minutes15**, каждый калибруется отдельно, своими сетками, свой
  литерал. 30m и 1h не калибруй: на 2026-10-11 30m провалил walk-forward на трёх тикерах из
  четырёх. Литералы `ParamsMinutes30`/`ParamsHour1` нового тикера — дефолты ядра. Исключение — прямая просьба
  владельца: тогда 30m/1h калибруются той же процедурой (`grids.py` знает их сетки глубины
  падения), а §5 выбирает среди всех откалиброванных таймфреймов.
- **Окно 36 месяцев на обоих таймфреймах**, walk-forward 12/6 (4 фолда). Окно 5m не сокращай:
  число сделок задают падения, а не число баров (≈ 40 сделок за 36 мес), короче — фолды вырождаются.
- **Одно ядро:** собранный бинарь, без `go run`:
  ```bash
  B=reports/drop_bounce_cal/backtest
  GOMAXPROCS=1 nice -n 19 go build -o $B ./cmd/backtest
  taskset -c 0 nice -n 19 env GOMAXPROCS=1 $B -strategy drop_bounce -metric profit_factor -months 36 -ticker <T> -interval <TF> ...
  ```
  Прогоны строго последовательно, в фоне (`run_in_background`), без двух бэктестов одновременно.
  Время на одном ядре: WF 15m ≈ 3 мин, WF 5m ≈ 13 мин, in-sample ≈ треть WF.
- **Сетки — сразу в `data/params/drop_bounce/<ticker>/`** (не scratchpad), генерирует их только
  `scripts/grids.py`. Каждая сетка прибивает все поля Params: у зарегистрированного тикера JSON
  ложится поверх его литерала, и неперечисленное поле молча придёт из старого литерала.
- **Сетку не меняй, пока по ней идут прогоны.** Поменял — перезапусти все прогоны этой сетки: таблица,
  где тикеры посчитаны на разных сетках, не сравнима.
- **Стоп обязателен в каждой точке.** Стоп меряется в дневных ATR (`StopDailyATR`, ATR заморожен
  на сигнале), в сетках нет `StopDailyATR = 0`. Никогда не выбирай точку без стопа, чтобы потом
  «приклеить» стоп: walk-forward тогда мерит одну стратегию, а литерал — другую.
- **Фильтр размаха дня `MaxDayRangeATR`** (вход, только если high−low дня до свечи-сигнала не больше
  этого числа дневных ATR) перебирается только своей фазой `day` в сетке `calstop`, вместе с
  вариантом 0 — фильтр выключен. Фильтр — часть точки, как стоп: не включай его поверх готовой
  точки отдельным прогоном и не выбрасывай из точки, если сетка его выбрала.
- **Объёмный фильтр `VolMult`/`VolBars`** (вход, только если объём свечи-сигнала не меньше `VolMult`
  средних объёмов `VolBars` свечей до неё) — то же правило: только своей фазой `volume` в сетке
  `calstop`, с вариантом 0 — выключен, и не отдельно от точки.
- **Отчёты** — `reports/<T>_drop_bounce/<шаг>/<TF>/` (вне git). По ним же продолжаешь после перерыва.
- **После каждого прогона** — строка `РЕЗУЛЬТАТ <дата>: ...` в `_comment` его сетки (pooled, фолды,
  вердикт скрипта). Вторая попытка — вторая строка `РЕЗУЛЬТАТ`, старые не стираются.

## 1. Пакет тикера

Если `internal/service/trading_strategy/drop_bounce/strategy/<ticker>/` нет — заведи его сразу:
четыре функции `ParamsMinutes5/15/30/Hour1`, все — явно выписанные `core.DefaultParams()`; тест
`TestLiteralsArePinned` со снимком всех четырёх; строка в `dropBounceRegistry` и в
`TestDropBounceTickerLiteralPerTimeframe`; тикер в списке drop_bounce в `CLAUDE.md`. Образец —
пакет `tbank`. Имя пакета — латиницей без цифр в начале (`T` → `tbank`). `go test
./internal/service/backtest/ ./internal/service/trading_strategy/drop_bounce/...` зелёный.

## 2. Baseline (на каждом таймфрейме)

`grids.py baseline <T> <TF>`, затем WF по `cal_<tf>_baseline.json`. Запиши pooled PF и число сделок.
Меньше 20 сделок за окно на таймфрейме — **СТОП для этого таймфрейма** (литерал — дефолты), учиться
не на чем. Baseline почти всегда ниже 1 — это нормально и значит одно: край есть только в связке
полей, поэтому дальше **фазовая** сетка, а не темы.

**Тематическую калибровку по одной оси поверх дефолтов не делай.** На 15m (GAZP, T, IVAT, WUSH)
все 20 тем были ниже 1, голоса ушли в дефолты, точки провалились: ось, полезная в связке, на
убыточном baseline не видна.

## 3. Фазовый walk-forward со стопом — судья таймфрейма

`grids.py calstop <T> <TF>` → `calstop_<tf>.json` (entry → risk → day → volume → exits, keepTop 3, ≈ 240 комбо):
entry — `MinDropPct`, `RSIPeriod`, `RSIEntry`; risk — `StopDailyATR` (0.25–1.0) ×
`ProfitPct`; day — `MaxDayRangeATR` (0, 0.5, 0.75, 1.0, 1.5) поверх трёх лучших risk; volume — `VolMult` (0, 1.5, 2, 3)
× `VolBars` (20, 50); exits —
`RSIExit` × `ExitInProfit` (0/1: крест RSI или %K в минусе откладывает выход до первого close выше входа) × `StochExit`. Фильтра тренда EMA и выхода MACD в стратегии больше нет (убраны 2026-10-12).
WF:
```
... -calibrate data/params/drop_bounce/<t>/calstop_<tf>.json -train-months 12 -test-months 6 -min-trades 10 -out reports/<T>_drop_bounce/wf/<TF>
python3 -I .../scripts/report.py wf <walkforward.md>
```
Каждый фолд заново проходит все фазы на своём train-окне, поэтому pooled OOS честный. Скрипт
печатает **ПЛАНКА ВЗЯТА / НЕ ВЗЯТА**: pooled PF ≥ 1.5, ≥ 20 сделок, ≥ 3 невырожденных фолда (≥ 5
сделок и хотя бы одна убыточная) и все, кроме максимум одного, выше 1.0. Меньше трёх живых фолдов —
планка не взята: данных нет, высокий PF на 1–3 сделках — шум.

Планка не взята — **таймфрейм отвергнут**. Других сеток, тем, зондов «а вдруг» не добавляй: каждая
лишняя попытка повышает шанс найти случайную удачу. Литерал таймфрейма остаётся дефолтами ядра.

## 4. Точка (только для таймфрейма, взявшего планку)

1. In-sample на полном окне той же сеткой: `-calibrate calstop_<tf>.json -min-trades 30 -out reports/<T>_drop_bounce/is/<TF>`.
2. `grids.py point <T> <TF> <calibration.md> 1` → `point_<tf>.json` (скрипт откажет, если стопа нет).
3. **Плато:** `grids.py plateau <T> <TF>`, затем in-sample прогоны `plateau_<tf>_entry.json`,
   `plateau_<tf>_stop.json` и для каждого фильтра, включённого в точке, — `plateau_<tf>_day.json`
   (`MaxDayRangeATR > 0`) и `plateau_<tf>_volume.json` (`VolMult > 0`); скрипт создаёт их только
   тогда, нижний сосед фильтра может быть 0 — выключен. Все с `-min-trades 1`,
   каждый — `report.py plateau <calibration.md> point_<tf>.json`. Все должны дать **ПЛАТО ЕСТЬ** (все соседи ≥ 1.0, медиана соседей ≥ 0.7 × PF точки). Острый
   пик → возьми комбо #2, затем #3 того же in-sample отчёта и повтори. Ни одна из трёх не держит
   плато → таймфрейм отвергнут.
4. **Издержки:** `-params data/params/drop_bounce/<t>/point_<tf>.json -commission 0.001 -out reports/<T>_drop_bounce/cost/<TF>`
   (обычный бэктест, без `-calibrate`), `report.py cost <отчёт.md>` → должно быть **ИЗДЕРЖКИ ВЫДЕРЖАНЫ**
   (PF ≥ 1.3 и net > 0). Нет → таймфрейм отвергнут.

## 5. Выбор таймфрейма

| Прошли §3–§4 | Решение |
|---|---|
| ни один | drop_bounce на тикере не торговать; литералы 5m/15m — дефолты |
| один | торговать на нём |
| оба | проверка совмещения ниже |

**Совмещение.** Два обычных бэктеста точек (`-params point_minutes5.json` и `point_minutes15.json`,
оба в один `-out reports/<T>_drop_bounce/overlap`), затем `scripts/overlap.py reports/<T>_drop_bounce/overlap <T>`.
Скрипт считает пересечение сделок по времени и проигрывает оба таймфрейма одной позицией на тикер.
- одна позиция дает PF ≥ 1.5 и сумму не ниже лучшего таймфрейма в одиночку → **торговать оба**;
- иначе → торговать один, с бо́льшим pooled OOS PF из §3 (при разнице < 0.1 — с бо́льшим числом сделок).

## 6. Литералы и запись

- Принятый таймфрейм: литерал = `point_<tf>.json`, числа явно; отвергнутый — дефолты ядра.
- Снимок в `<ticker>_test.go` обновлён, `go test` из §1 зелёный.
- Doc-комментарий пакета: дата, сетки, по каждому из 5m/15m — pooled OOS (сделки, фолды), стоп в
  ATR, фильтр размаха дня и объёмный фильтр точки (или «выключен»), плато,
  издержки, решение §5 и, если оба, итог совмещения. Это единственное место записи про тикер:
  `docs/drop_bounce/` описывает механику и не принимает калибровочные отчёты.
- `РЕЗУЛЬТАТ` во всех сетках тикера.
- Не коммить, пока владелец не попросил.

## Красные флаги — остановись

| Мысль | Что на самом деле |
|---|---|
| «Лучшая точка без стопа, стоп добавлю потом» | WF мерил другую стратегию. Стоп только внутри сетки. |
| «Давай по темам, как в rsi_zone» | Работает лишь над прибыльным baseline. Здесь baseline < 1. |
| «In-sample PF 4+, значит работает» | Судья — pooled OOS WF. In-sample только выбирает точку. |
| «PF 3.8 на двух живых фолдах — отличный результат» | Меньше трёх живых фолдов — данных нет. |
| «Планка не взята, попробую ещё сетку/фазу» | Повторные попытки = подгонка. Таймфрейм отвергнут. |
| «Окно 5m долгое, сокращу до 18 месяцев» | Сделок станет вдвое меньше, фолды выродятся. |
| «Поправлю сетку, пока идёт очередь» | Таблица станет несравнимой. Правка → перезапуск всех её прогонов. |
| «Запущу два бэктеста параллельно» | Одно ядро, строго последовательно. |
| «Точка готова, добавлю фильтр размаха дня / объёма сверху» | Фильтр меняет набор сделок — WF мерил другую стратегию. Только фазой `day` / `volume`. |
